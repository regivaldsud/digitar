Aula 150 · Princípios SOLID em Python

Nesta aula você vai aprender

  • Saber o que significa cada letra de SOLID e por que esses conselhos existem
  • Separar responsabilidades em classes e funções pequenas (S)
  • Acrescentar comportamento novo sem mexer no que já funciona (O)
  • Garantir que uma classe filha possa substituir a mãe sem surpresas (L)
  • Criar interfaces pequenas e depender de abstrações, não de detalhes (I e D)

Por que existem princípios de projeto

Programas pequenos cabem na cabeça. Quando o programa cresce, cada mudança começa a quebrar outra coisa lá longe. Quase sempre o motivo é o mesmo: partes do código dependem demais umas das outras.

SOLID é um conjunto de cinco conselhos, juntados pelo programador Robert C. Martin, para escrever classes que continuam fáceis de mudar. O nome vem da primeira letra de cada princípio em inglês:

  • S — Single responsibility (responsabilidade única): cada classe cuida de uma coisa só.
  • O — Open/closed (aberto/fechado): dá para acrescentar comportamento sem reescrever o que já funciona.
  • L — Liskov substitution (substituição de Liskov): a filha funciona em qualquer lugar onde a mãe funciona.
  • I — Interface segregation (segregação de interfaces): várias interfaces pequenas são melhores que uma enorme.
  • D — Dependency inversion (inversão de dependência): dependa de abstrações, não de detalhes.

Eles não são leis. São perguntas que você faz quando o código começa a doer: "se eu mudar isto, o que mais quebra?".

S: uma responsabilidade por classe

Uma classe tem "uma responsabilidade" quando existe um só motivo para ela mudar. Veja um boletim que calcula a média, monta o texto e ainda "salva":

class Boletim:
    def __init__(self, aluno, notas):
        self.aluno = aluno
        self.notas = notas

    def processar(self):
        media = sum(self.notas) / len(self.notas)       # cálculo
        texto = f"{self.aluno}: média {media:.1f}"     # apresentação
        print("Salvando:", texto)                     # armazenamento
        return texto


Boletim("Marina", [8, 7.5, 9]).processar()

Salvando: Marina: média 8.2

Se a escola mudar o jeito de calcular a média, você mexe nessa classe. Se mudar o formato do texto, mexe de novo. Se trocar o lugar onde salva, de novo. Três motivos para mudar no mesmo lugar. Separando, cada parte muda sozinha:

class Boletim:
    def __init__(self, aluno, notas):
        self.aluno = aluno
        self.notas = notas

    def media(self):
        return sum(self.notas) / len(self.notas)


def formatar(boletim):
    return f"{boletim.aluno}: média {boletim.media():.1f}"


class Arquivo:
    def __init__(self):
        self.linhas = []

    def salvar(self, texto):
        self.linhas.append(texto)


b = Boletim("Marina", [8, 7.5, 9])
arquivo = Arquivo()
arquivo.salvar(formatar(b))
print(arquivo.linhas)

['Marina: média 8.2']

Dica: Em Python, nem tudo precisa ser classe. Uma função simples como formatar já é uma "responsabilidade única" perfeita.

O: aberto para estender, fechado para modificar

Uma loja calcula o frete com uma fila de if. Cada transportadora nova obriga você a abrir e editar essa função, correndo o risco de estragar as que já funcionavam:

def frete(tipo, peso):
    if tipo == "correio":
        return 10 + peso * 2
    elif tipo == "moto":
        return 15.0
    # nova transportadora? mais um elif aqui dentro...
    raise ValueError("tipo desconhecido")


print(frete("correio", 3))
print(frete("moto", 3))

16
15.0

A versão "aberta para extensão" guarda cada regra num objeto separado. Para uma transportadora nova, você acrescenta uma classe; a função cotar não muda:

class Correio:
    def preco(self, peso):
        return 10 + peso * 2


class Motoboy:
    def preco(self, peso):
        return 15.0


class Drone:                      # novidade: nenhuma linha antiga mudou
    def preco(self, peso):
        return 30.0 if peso <= 2 else 60.0


def cotar(transportadoras, peso):
    for t in transportadoras:
        print(f"{type(t).__name__:<8} R$ {t.preco(peso):.2f}")


cotar([Correio(), Motoboy(), Drone()], 3)

Correio  R$ 16.00
Motoboy  R$ 15.00
Drone    R$ 60.00

L: a filha precisa servir no lugar da mãe

A aula 79 mostrou o princípio de Liskov: se uma função recebe um Passaro, qualquer filha de Passaro deve funcionar ali sem surpresa. O exemplo clássico de erro é o quadrado que herda do retângulo:

class Retangulo:
    def __init__(self, largura, altura):
        self.largura = largura
        self.altura = altura

    def definir_largura(self, valor):
        self.largura = valor

    def area(self):
        return self.largura * self.altura


class Quadrado(Retangulo):
    def __init__(self, lado):
        super().__init__(lado, lado)

    def definir_largura(self, valor):   # quadrado muda os dois lados!
        self.largura = valor
        self.altura = valor


def dobrar_largura(r):
    r.definir_largura(r.largura * 2)
    return r.area()


print("Retângulo 2x3 ->", dobrar_largura(Retangulo(2, 3)), "(esperado 12)")
print("Quadrado 2x2  ->", dobrar_largura(Quadrado(2)), "(esperado 8)")

Retângulo 2x3 -> 12 (esperado 12)
Quadrado 2x2  -> 16 (esperado 8)

Quem escreveu dobrar_largura contava que a altura não mudaria. O Quadrado quebrou essa promessa. A saída é não forçar a herança: Quadrado e Retangulo podem ser classes irmãs, filhas de uma Forma que só promete area().

Atenção: "É um" na vida real não garante herança no código. Pergunte: a filha cumpre todas as promessas da mãe? Se ela precisa desligar ou mudar o sentido de um método, a herança está errada.

I: interfaces pequenas

Se uma interface obriga todo mundo a ter métodos que não fazem sentido, as classes acabam com métodos "falsos" que só dão erro. Separe em pedaços pequenos e cada classe pega só o que usa:

from abc import ABC, abstractmethod


class Imprime(ABC):
    @abstractmethod
    def imprimir(self, texto): ...


class Digitaliza(ABC):
    @abstractmethod
    def digitalizar(self): ...


class ImpressoraSimples(Imprime):
    def imprimir(self, texto):
        print("Imprimindo:", texto)


class Multifuncional(Imprime, Digitaliza):
    def imprimir(self, texto):
        print("Multifuncional imprime:", texto)

    def digitalizar(self):
        return "imagem.png"


for aparelho in [ImpressoraSimples(), Multifuncional()]:
    aparelho.imprimir("prova de matemática")
    if isinstance(aparelho, Digitaliza):
        print("  digitalizou:", aparelho.digitalizar())

Imprimindo: prova de matemática
Multifuncional imprime: prova de matemática
  digitalizou: imagem.png

Sem essa separação, a ImpressoraSimples teria um digitalizar() que só faria raise NotImplementedError — uma armadilha para quem a usasse.

D: dependa de abstrações

Quando uma classe cria por conta própria os objetos de que precisa, ela fica presa a eles. Na inversão de dependência, ela recebe o objeto pronto (de fora) e só conhece a "ideia" dele. Isso facilita trocar a peça e, principalmente, testar:

from typing import Protocol


class Notificador(Protocol):
    def enviar(self, para: str, texto: str) -> None: ...


class EmailFalso:
    def __init__(self):
        self.enviados = []

    def enviar(self, para, texto):
        self.enviados.append((para, texto))


class Escola:
    def __init__(self, notificador: Notificador):   # recebe de fora
        self.notificador = notificador

    def avisar_falta(self, aluno):
        self.notificador.enviar(f"pais de {aluno}", f"{aluno} faltou hoje")


email = EmailFalso()
Escola(email).avisar_falta("Theo")
print(email.enviados)

[('pais de Theo', 'Theo faltou hoje')]

Escola não sabe se a mensagem vai por e-mail, WhatsApp ou SMS. No teste usamos um EmailFalso que só guarda as mensagens — a mesma ideia dos mocks da aula 133. Protocol (aula 91) descreve "qualquer objeto que tenha enviar", sem obrigar herança.

Quando usar e quando é exagero

SOLID ajuda quando o código já está mudando e as mudanças doem. Um script de 30 linhas que roda uma vez não precisa de cinco classes e três interfaces.

Dica: Uma boa regra: escreva do jeito simples primeiro. Quando aparecer o segundo ou terceiro caso parecido (a segunda transportadora, o segundo tipo de aviso), aí sim separe.
Atenção: Exagerar também é um erro: classes demais, cada uma com uma linha, deixam o programa difícil de seguir. O objetivo de SOLID é facilitar a mudança, não deixar o código "bonito".
Pratique no DIGITAR: digite este trecho no modo Programar do app. 
def __init__(self, notificador: Notificador):

Exercícios

1. Esta classe Pedido calcula o total e também monta o recibo em texto. Separe a montagem do recibo numa função recibo(pedido), mantendo o cálculo na classe.

Ver resposta 
class Pedido:
    def __init__(self, itens):
        self.itens = itens  # lista de (nome, preço)

    def total(self):
        return sum(preco for _, preco in self.itens)


def recibo(pedido):
    linhas = [f"{nome:<10} R$ {preco:6.2f}" for nome, preco in pedido.itens]
    linhas.append(f"{'TOTAL':<10} R$ {pedido.total():6.2f}")
    return "\n".join(linhas)


print(recibo(Pedido([("Caderno", 18.5), ("Lápis", 2.0)])))

Caderno    R$  18.50
Lápis      R$   2.00
TOTAL      R$  20.50

Agora mudar o visual do recibo não mexe no cálculo, e o cálculo pode ser testado sem olhar texto nenhum.

2. Aplique o princípio aberto/fechado a um sistema de descontos: crie as classes SemDesconto, DezPorCento e MenosCinco (tira R$ 5), todas com o método aplicar(valor), e uma função caixa(valor, desconto) que não precise mudar quando um desconto novo aparecer.

Ver resposta 
class SemDesconto:
    def aplicar(self, valor):
        return valor


class DezPorCento:
    def aplicar(self, valor):
        return valor * 0.9


class MenosCinco:
    def aplicar(self, valor):
        return max(valor - 5, 0)


def caixa(valor, desconto):
    return f"R$ {desconto.aplicar(valor):.2f}"


for d in [SemDesconto(), DezPorCento(), MenosCinco()]:
    print(type(d).__name__, caixa(40, d))

SemDesconto R$ 40.00
DezPorCento R$ 36.00
MenosCinco R$ 35.00

3. Uma classe Pinguim herda de Passaro, mas o método voar() dela faz raise Exception("não voo"). Qual princípio está sendo quebrado e como resolver?

Ver resposta

O princípio de Liskov (L): quem recebe um Passaro espera poder chamar voar(),
e o Pinguim quebra essa promessa. Solução: tirar voar() de Passaro e criar
uma classe ou interface separada (por exemplo, PassaroQueVoa) só para quem voa.

4. Reescreva a classe abaixo para receber o "relógio" de fora (inversão de dependência), de modo que dê para testar a saudação da manhã e da noite sem esperar o horário certo.

Ver resposta 
class Saudacao:
    def __init__(self, hora_atual):
        self.hora_atual = hora_atual    # uma função que devolve a hora

    def texto(self):
        hora = self.hora_atual()
        return "Bom dia!" if hora < 12 else "Boa noite!" if hora >= 18 else "Boa tarde!"


print(Saudacao(lambda: 8).texto())
print(Saudacao(lambda: 15).texto())
print(Saudacao(lambda: 21).texto())

Bom dia!
Boa tarde!
Boa noite!

No programa de verdade você passaria lambda: datetime.now().hour; no teste, um número fixo.

5. Por que uma interface Funcionario com os métodos dar_aula(), limpar_sala() e dirigir_onibus() é uma má ideia numa escola? Que princípio ela quebra?

Ver resposta

Ela quebra a segregação de interfaces (I). Uma professora teria de "implementar"
limpar_sala() e dirigir_onibus() mesmo sem fazer isso. O melhor é ter interfaces
pequenas (DaAula, Limpa, Dirige), e cada classe herda só as que usa.
