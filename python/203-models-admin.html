Models: tabelas escritas em Python

No módulo 9 você criou tabelas escrevendo SQL: CREATE TABLE, INSERT, SELECT. Funciona, mas é fácil errar uma vírgula, e cada banco (SQLite, PostgreSQL, MySQL) tem as suas diferenças.

No Django, você descreve a tabela como uma classe Python, chamada model. Cada atributo da classe é uma coluna, e cada objeto é uma linha. O Django escreve o SQL por você, no "sotaque" do banco que estiver usando.

Arquivo contatos/models.py:

from django.db import models


class Contato(models.Model):
    nome = models.CharField(max_length=100)
    telefone = models.CharField(max_length=20)
    email = models.EmailField(blank=True)
    nascimento = models.DateField(null=True, blank=True)
    favorito = models.BooleanField(default=False)
    criado_em = models.DateTimeField(auto_now_add=True)

    class Meta:
        ordering = ["nome"]

    def __str__(self):
        return self.nome

Esse código sozinho ainda não muda nada no banco: ele é a descrição da tabela. Quem cria a tabela de verdade é a migração, logo abaixo. O Django ainda acrescenta sozinho uma coluna id, a chave primária (aula 170), que numera os contatos.

Os tipos de campo e as opções

Cada campo diz que tipo de dado a coluna guarda e já traz validações:

  • CharField(max_length=...): texto curto, com tamanho máximo obrigatório;
  • TextField(): texto longo, como a descrição de uma receita;
  • IntegerField() e PositiveIntegerField(): números inteiros (o segundo não aceita negativos);
  • DecimalField(max_digits=8, decimal_places=2): dinheiro, sem a imprecisão do float (aula 29);
  • BooleanField(): verdadeiro ou falso;
  • DateField() e DateTimeField(): data, ou data e hora (aula 101);
  • EmailField(): um CharField que confere se o texto parece um e-mail.

E as opções mais usadas:

  • blank=True: o campo pode ficar vazio nos formulários (aula 205);
  • null=True: o banco aceita "sem valor" (NULL). Use em datas e números opcionais; em textos, prefira só blank=True, que guarda o texto vazio "";
  • default=...: o valor quando ninguém informar outro;
  • auto_now_add=True: grava a data e hora da criação sozinho.

O class Meta guarda configurações do model: ordering = ["nome"] faz toda busca vir em ordem alfabética. O __str__ (aula 81) define como cada contato aparece no shell e no admin.

O que um model faz por dentro? Ele é uma descrição que vira SQL. Veja a ideia num "mini Django" em Python puro, que gera o CREATE TABLE a partir de uma lista de campos e o roda no SQLite:

import sqlite3

TIPOS = {"texto": "varchar(100)", "inteiro": "integer", "booleano": "bool"}

campos_do_model = {
    "nome": "texto",
    "idade": "inteiro",
    "favorito": "booleano",
}


def gerar_create(tabela, campos):
    colunas = ['"id" integer NOT NULL PRIMARY KEY AUTOINCREMENT']
    for nome, tipo in campos.items():
        colunas.append(f'"{nome}" {TIPOS[tipo]} NOT NULL')
    return f'CREATE TABLE "{tabela}" (' + ", ".join(colunas) + ");"


sql = gerar_create("contatos_amigo", campos_do_model)
print(sql)

con = sqlite3.connect(":memory:")
con.execute(sql)
for coluna in con.execute("PRAGMA table_info(contatos_amigo)"):
    print(coluna[1], "->", coluna[2])
con.close()

CREATE TABLE "contatos_amigo" ("id" integer NOT NULL PRIMARY KEY AUTOINCREMENT, "nome" varchar(100) NOT NULL, "idade" integer NOT NULL, "favorito" bool NOT NULL);
id -> INTEGER
nome -> varchar(100)
idade -> INTEGER
favorito -> bool

O nome da tabela segue o padrão do Django: nomedoapp_nomedomodel, tudo em minúsculas.

Migrações: levando o model para o banco

Uma migração é um arquivo Python, guardado na pasta contatos/migrations/, que lista as mudanças a fazer no banco. O trabalho tem dois passos, e você vai repetir esses dois comandos toda vez que mudar um model:

python manage.py makemigrations
python manage.py migrate

O primeiro escreve o arquivo da migração comparando o model com a última migração. O segundo aplica no banco as migrações que ainda não rodaram. Na primeira vez, o migrate também cria as tabelas dos apps que já vêm com o Django (usuários, sessões, admin):

Migrations for 'contatos':
  contatos\migrations\0001_initial.py
    + Create model Contato
Operations to perform:
  Apply all migrations: admin, auth, contatos, contenttypes, sessions
Running migrations:
  Applying contenttypes.0001_initial... OK
  Applying auth.0001_initial... OK
  (... outras linhas parecidas ...)
  Applying contatos.0001_initial... OK
  Applying sessions.0001_initial... OK

Por padrão, o banco é o arquivo SQLite db.sqlite3, na pasta do projeto (aula 174). Quer ver o SQL que a migração gerou? Use o sqlmigrate:

python manage.py sqlmigrate contatos 0001

BEGIN;
--
-- Create model Contato
--
CREATE TABLE "contatos_contato" ("id" integer NOT NULL PRIMARY KEY AUTOINCREMENT, "nome" varchar(100) NOT NULL, "telefone" varchar(20) NOT NULL, "email" varchar(254) NOT NULL, "nascimento" date NULL, "favorito" bool NOT NULL, "criado_em" datetime NOT NULL);
COMMIT;

Compare com o model: max_length=100 virou varchar(100), o null=True da data virou date NULL, e todos os outros campos ficaram NOT NULL.

Atenção: Mudou o model e a página mostra no such table: contatos_contato ou no such column? Você esqueceu o makemigrations e o migrate. E se o makemigrations responder No changes detected, confira se o app está em INSTALLED_APPS e se você salvou o models.py.
Dica: Os arquivos da pasta migrations fazem parte do projeto: guarde-os no Git (aula 244). É com eles que o banco de outro computador, ou do servidor, fica igual ao seu.

Mudando um model que já tem dados

Agora imagine que o banco já tem contatos e você acrescenta apelido = models.CharField(max_length=50). O que o banco deve pôr nas linhas antigas? Como o campo é NOT NULL e não tem padrão, o makemigrations para e pergunta:

It is impossible to add a non-nullable field 'apelido' to contato without specifying a default. This is because the database needs something to populate existing rows.
Please select a fix:
 1) Provide a one-off default now (will be set on all existing rows with a null value for this column)
 2) Quit and manually define a default value in models.py.
Select an option:

O jeito mais simples é escolher a opção 2 e dar um padrão no próprio model: apelido = models.CharField(max_length=50, blank=True, default=""). Veja no SQLite o mesmo problema e a mesma solução — a coluna nova precisa de um valor para as linhas que já existiam:

import sqlite3

con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE contatos (id INTEGER PRIMARY KEY, nome TEXT NOT NULL)")
con.execute("INSERT INTO contatos (nome) VALUES ('Ana')")
con.execute("INSERT INTO contatos (nome) VALUES ('Bruno')")

try:
    con.execute("ALTER TABLE contatos ADD COLUMN apelido TEXT NOT NULL")
except sqlite3.OperationalError as erro:
    print("Sem padrão:", erro)

con.execute("ALTER TABLE contatos ADD COLUMN apelido TEXT NOT NULL DEFAULT ''")
for linha in con.execute("SELECT id, nome, apelido FROM contatos"):
    print(linha)
con.close()

Sem padrão: Cannot add a NOT NULL column with default value NULL
(1, 'Ana', '')
(2, 'Bruno', '')

Depois de corrigir o model, rode makemigrations (que cria 0002_contato_apelido.py) e migrate.

Usando o model no shell

O python manage.py shell abre o Python já com o seu projeto carregado. É ótimo para experimentar o model (a aula 204 aprofunda as buscas):

from contatos.models import Contato

ana = Contato.objects.create(nome="Ana", telefone="81 99999-0000", favorito=True)
print(ana.id, ana.nome, ana.favorito)
print(ana)
print(repr(ana))
print(Contato.objects.count())

Ana
<Contato: Ana>
1

O print(ana) mostra Ana por causa do __str__. Sem ele, apareceria o pouco útil Contato object (1).

A área administrativa

O Django vem com um painel pronto para cadastrar, editar, buscar e apagar dados: o admin. Para um model aparecer lá, registre-o.

Arquivo contatos/admin.py:

from django.contrib import admin

from .models import Contato


@admin.register(Contato)
class ContatoAdmin(admin.ModelAdmin):
    list_display = ["nome", "telefone", "favorito"]
    search_fields = ["nome", "email"]
    list_filter = ["favorito"]
  • list_display: as colunas da lista de contatos;
  • search_fields: os campos em que a caixa de busca procura;
  • list_filter: os filtros da barra lateral (ex.: só os favoritos).

Para entrar no admin é preciso um usuário administrador. Crie o seu e ligue o servidor:

python manage.py createsuperuser
python manage.py runserver

O createsuperuser pergunta o nome de usuário, o e-mail (pode deixar vazio) e a senha duas vezes; a senha não aparece enquanto você digita. Entre em http://127.0.0.1:8000/admin/: depois do login aparece "Administração do Site" com o grupo Contatos. Clicando nele, você vê a tabela com as colunas Nome, Telefone e Favorito, a caixa de busca e o filtro "Por favorito" à direita. Buscando car, só a Carla aparece.

Dica: O admin é para você e a sua equipe, não para os visitantes do site. Para os visitantes, você vai criar páginas próprias com formulários (aulas 205 e 207).
Pratique no DIGITAR: digite este trecho no modo Programar do app. 
nome = models.CharField(max_length=100)

2. Você acrescentou apelido = models.CharField(max_length=50) num model que já tem dados, e o makemigrations perguntou o que fazer com as linhas antigas. Qual é a saída mais simples?

Ver resposta 
from django.db import models

apelido = models.CharField(max_length=50, blank=True, default="")

Com default="", os contatos antigos recebem um apelido vazio, e blank=True deixa o campo opcional nos formulários.

6. Qual é a diferença entre blank=True e null=True?

Ver resposta

blank=True  -> vale para os formulários e o admin: o campo pode ficar em branco.
null=True   -> vale para o banco: a coluna aceita NULL ("sem valor").
Em datas e números opcionais, use os dois. Em textos, use só blank=True:
o vazio fica guardado como "" e você não tem dois tipos de "vazio" (None e "").
