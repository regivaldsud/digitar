Senha nunca em texto puro

Se um site guarda as senhas como texto e alguém rouba o banco de dados, o ladrão lê todas as senhas — e muita gente usa a mesma senha em vários lugares. Por isso, sites sérios guardam só um hash: um "resumo" da senha, calculado por uma conta que só funciona num sentido. Da senha se chega ao hash; do hash não se volta à senha.

import hashlib

for senha in ["girassol", "girassol", "Girassol"]:
    resumo = hashlib.sha256(senha.encode()).hexdigest()
    print(senha, "->", resumo[:20] + "...")

girassol -> 72c3179e035de99f3f30...
girassol -> 72c3179e035de99f3f30...
Girassol -> a2437c7acf50490de674...

A mesma senha dá sempre o mesmo hash, e uma letra diferente muda tudo. Mas isso tem um problema: duas pessoas com a senha girassol teriam o mesmo hash, e um ladrão poderia usar uma tabela pronta de senhas comuns. A solução é o sal: um texto aleatório, diferente para cada usuário, misturado à senha antes do cálculo. E, para atrasar quem tenta adivinhar, a conta é repetida milhares de vezes.

Como o Django guarda a senha

O Django usa o algoritmo PBKDF2 com sal e muitas repetições. Dá para fazer o mesmo com a biblioteca padrão:

import base64
import hashlib


def gerar_hash(senha, sal, repeticoes=50_000):
    bruto = hashlib.pbkdf2_hmac("sha256", senha.encode(), sal.encode(), repeticoes)
    return f"pbkdf2_sha256${repeticoes}${sal}${base64.b64encode(bruto).decode()}"


print(gerar_hash("girassol", sal="Xy7Qa2"))
print(gerar_hash("girassol", sal="Lm0Pz9"))

pbkdf2_sha256$50000$Xy7Qa2$Mjk27Bgbwv3WURFbBERpkYeOsILZ07OeWa4MnjZdZmg=
pbkdf2_sha256$50000$Lm0Pz9$8pNxsvko1CVCsNIEsEZxLgukpLrNn4syNmVuWVrOb6U=

Mesma senha, sais diferentes, hashes completamente diferentes. O texto guardado tem quatro partes separadas por $: o algoritmo, as repetições, o sal e o resultado. É exatamente esse o formato que o Django grava na coluna password da tabela de usuários (lá, as repetições passam de um milhão).

Para conferir uma senha no login, o site pega o sal guardado, refaz a conta com o que a pessoa digitou e compara:

import base64
import hashlib
import hmac


def gerar_hash(senha, sal, repeticoes=50_000):
    bruto = hashlib.pbkdf2_hmac("sha256", senha.encode(), sal.encode(), repeticoes)
    return f"pbkdf2_sha256${repeticoes}${sal}${base64.b64encode(bruto).decode()}"


def confere(senha_digitada, guardado):
    algoritmo, repeticoes, sal, _ = guardado.split("$")
    tentativa = gerar_hash(senha_digitada, sal, int(repeticoes))
    return hmac.compare_digest(tentativa, guardado)


no_banco = gerar_hash("girassol-azul-42", sal="Xy7Qa2")
print(confere("girassol-azul-42", no_banco))
print(confere("girassol", no_banco))

True
False

Dica: hmac.compare_digest compara textos sempre no mesmo tempo, não importa onde está a primeira diferença. Um == comum para no primeiro caractere diferente, e um atacante muito paciente poderia medir esse tempo. Detalhe pequeno, mas é assim que se faz.
Atenção: Isso é para você entender o que acontece. Num projeto de verdade, nunca invente o seu próprio sistema de senhas: use o do Django, que já é testado e atualizado. E nunca grave senha num campo comum de model, como models.CharField.

Criando usuários no Django

O Django já tem o model User, com nome de usuário, e-mail e senha. O método create_user cria o usuário e calcula o hash. Teste no python manage.py shell:

from django.contrib.auth.models import User

ana = User.objects.create_user("ana", password="girassol-azul-42")
print(ana.password[:22] + "...")
print(ana.check_password("girassol-azul-42"))
print(ana.check_password("girassol"))
print(ana.is_authenticated)

pbkdf2_sha256$1500000$...
True
False
True

O número de repetições pode mudar de uma versão do Django para outra. Para criar um administrador, continue usando python manage.py createsuperuser (aula 203).

Atenção: Nunca faça User.objects.create(username="ana", password="girassol"): o create comum grava a senha como texto puro e o login nunca vai funcionar. Use create_user, ou usuario.set_password("...") seguido de usuario.save().

Login e logout prontos

O Django já traz as páginas de entrar, sair e trocar senha. Basta incluir as URLs dele no config/urls.py:

# config/urls.py
from django.contrib import admin
from django.urls import include, path

urlpatterns = [
    path("admin/", admin.site.urls),
    path("contas/", include("django.contrib.auth.urls")),
    path("", include("contatos.urls")),
]

/contas/login/  -> página de login (nome da URL: "login")
/contas/logout/ -> sair, só por POST (nome da URL: "logout")

E diga ao Django para onde mandar as pessoas, no fim do config/settings.py:

# config/settings.py (trecho)
LOGIN_URL = "login"              # quem não entrou vai para cá
LOGIN_REDIRECT_URL = "lista"     # depois de entrar
LOGOUT_REDIRECT_URL = "login"    # depois de sair

(sem saída: são só configurações)

Falta o template do login. Ele precisa se chamar registration/login.html; crie em contatos/templates/registration/login.html:

{% extends "base.html" %}
{% block conteudo %}
<h1>Entrar</h1>
<form method="post">
  {% csrf_token %}
  {{ form.as_p }}
  <input type="hidden" name="next" value="{{ next }}">
  <button type="submit">Entrar</button>
</form>
{% endblock %}

O campo escondido next guarda a página que a pessoa queria ver antes de ser mandada para o login; depois de entrar, ela volta para lá.

Atenção: Desde o Django 5, o logout só aceita POST: um link <a href="/contas/logout/"> dá erro 405. Use um formulário com {% csrf_token %} e um botão "Sair" (veja o exercício 1).

A sessão: como o site lembra de você

A web "esquece" tudo entre um pedido e outro. Depois do login, como o site sabe que o próximo clique também é seu? Com a sessão: o servidor guarda "este visitante é a Ana" numa tabela e entrega ao navegador só um número de sorteio num cookie. A cada clique, o navegador devolve o cookie e o servidor procura o número. Uma simulação com dicionário:

import secrets

sessoes = {}   # no Django, fica na tabela django_session


def fazer_login(usuario):
    chave = secrets.token_hex(8)
    sessoes[chave] = {"usuario": usuario}
    return chave            # vai para o navegador como cookie "sessionid"


def quem_e(cookie):
    sessao = sessoes.get(cookie)
    return sessao["usuario"] if sessao else None


cookie_da_ana = fazer_login("ana")
print("Com o cookie certo:", quem_e(cookie_da_ana))
print("Com um cookie inventado:", quem_e("1234"))
del sessoes[cookie_da_ana]          # é isso que o logout faz
print("Depois do logout:", quem_e(cookie_da_ana))

Com o cookie certo: ana
Com um cookie inventado: None
Depois do logout: None

No Django, quem faz esse trabalho é o SessionMiddleware e o AuthenticationMiddleware, que já vêm ligados. Em toda view, request.user é o usuário logado — ou um usuário "anônimo", com request.user.is_authenticated igual a False.

Protegendo páginas com @login_required

@login_required é um decorador, como os da aula 56: ele "embrulha" a view e, se ninguém entrou, manda para o LOGIN_URL. Veja a ideia em Python puro:

from functools import wraps


def login_obrigatorio(view):
    @wraps(view)
    def embrulho(request):
        if request.get("usuario") is None:
            return "302 -> /contas/login/?next=" + request["caminho"]
        return view(request)
    return embrulho


@login_obrigatorio
def lista(request):
    return "200 -> contatos de " + request["usuario"]


print(lista({"caminho": "/", "usuario": "ana"}))
print(lista({"caminho": "/", "usuario": None}))

200 -> contatos de ana
302 -> /contas/login/?next=/

No Django, é só importar e usar, em contatos/views.py:

# contatos/views.py
from django.contrib.auth.decorators import login_required
from django.shortcuts import render
from .models import Contato


@login_required
def lista(request):
    contatos = Contato.objects.filter(dono=request.user)
    return render(request, "contatos/lista.html", {"contatos": contatos})

Sem login:  GET /  -> 302 para /contas/login/?next=/
Com login:  GET /  -> 200, só os contatos de quem entrou

Cada um com os seus contatos

Para cada pessoa ver só os próprios contatos, o model Contato ganha um dono: uma chave estrangeira (aula 173) para o usuário. Em contatos/models.py, acrescente o campo e rode makemigrations e migrate:

# contatos/models.py (trecho)
from django.conf import settings
from django.db import models


class Contato(models.Model):
    dono = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE)
    nome = models.CharField(max_length=100)
    # ... os outros campos da aula 203 continuam iguais

(o makemigrations vai perguntar o dono dos contatos que já existem: responda 1 e digite o id de um usuário, por exemplo 1)

settings.AUTH_USER_MODEL aponta para o model de usuário do projeto. on_delete=models.CASCADE apaga os contatos quando o usuário é apagado. Em qualquer template, {% if user.is_authenticated %}Olá, {{ user.username }}!{% endif %} mostra quem está logado.

Página de cadastro

Para qualquer pessoa criar a própria conta, o Django tem o UserCreationForm, que já pede a senha duas vezes e confere se ela é forte o bastante.

# contatos/views.py (acrescente)
from django.contrib.auth import login
from django.contrib.auth.forms import UserCreationForm
from django.shortcuts import redirect, render


def cadastro(request):
    form = UserCreationForm(request.POST or None)
    if form.is_valid():
        usuario = form.save()
        login(request, usuario)
        return redirect("lista")
    return render(request, "registration/cadastro.html", {"form": form})

# contatos/urls.py: path("cadastro/", views.cadastro, name="cadastro"),

POST /cadastro/ com senha "123"  -> 200, erros como "Esta senha é muito curta."
POST /cadastro/ com senha forte  -> 302, conta criada e já logada

request.POST or None é um atalho: no GET o formulário nasce vazio (e is_valid() dá False sem mostrar erros); no POST ele recebe os dados.

4. Mude o decorador login_obrigatorio para um so_admin, que só deixa passar quando request["usuario"] for "admin" e, para os outros, devolve "403 -> proibido".

Ver resposta 
from functools import wraps


def so_admin(view):
    @wraps(view)
    def embrulho(request):
        if request.get("usuario") != "admin":
            return "403 -> proibido"
        return view(request)
    return embrulho


@so_admin
def painel(request):
    return "200 -> painel"


print(painel({"usuario": "admin"}))
print(painel({"usuario": "ana"}))
print(painel.__name__)

200 -> painel
403 -> proibido
painel

O @wraps mantém o nome painel na função embrulhada. No Django existe algo parecido: @user_passes_test(lambda u: u.is_staff).
