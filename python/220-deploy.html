Nesta aula você vai aprender

  • Entender o caminho de um pedido em produção: Nginx, Gunicorn, Django e PostgreSQL
  • Preparar o settings.py para produção, lendo os segredos de variáveis de ambiente

  • Rodar o Gunicorn como serviço do systemd e o Nginx na frente dele
  • Ativar o HTTPS com Certbot e conferir a segurança com check --deploy
Aula para fazer no computador: o assunto desta aula precisa do seu computador. Os códigos sem o botão Executar devem ser copiados para um arquivo .py no VS Code e rodados no seu computador, como mostrado na aula 03.

Por que não publicar com o runserver

O python manage.py runserver foi feito para você programar: ele atende um pedido por vez, recarrega quando o código muda e mostra páginas de erro detalhadas. Na internet, isso seria lento e perigoso. Um site publicado ("em produção") usa várias peças, cada uma boa no seu trabalho:

Navegador --HTTPS--> Nginx --> Gunicorn --> Django --> PostgreSQL
                       |
                       +--> /static/ e /media/ (entregues direto do disco)

  • Nginx fica na porta da frente: recebe os pedidos da internet, cuida do HTTPS e entrega CSS, imagens e arquivos enviados direto do disco, sem incomodar o Python;
  • Gunicorn roda o seu Django com vários processos ao mesmo tempo, para atender muita gente;
  • PostgreSQL é o banco de dados, mais robusto que o SQLite quando muitas pessoas escrevem ao mesmo tempo;
  • systemd é o "gerente" do Linux: liga o Gunicorn quando o servidor inicia e o religa se ele cair.

O servidor costuma ser uma VPS: um computador Linux (aqui, Ubuntu) alugado num serviço de nuvem, que você controla pelo terminal. Você também vai precisar de um domínio (como meusite.com.br) apontando para o endereço IP do servidor.

Dica: Para o primeiro site, uma plataforma que publica direto do GitHub faz a maior parte destes passos por você. Montar o servidor na mão, como nesta aula, é ótimo para entender o que essas plataformas fazem por baixo.

Passo 1: o settings.py de produção

Em produção, três coisas mudam: DEBUG fica desligado, só os seus domínios são aceitos e os segredos (a SECRET_KEY, a senha do banco) saem do código e vêm de variáveis de ambiente (aulas 108 e 177). Assim o mesmo código roda no seu computador e no servidor, e nenhuma senha vai para o GitHub.

Primeiro, veja como ler e converter configurações do ambiente. Variáveis de ambiente são sempre texto, então "False" precisa virar False e "a.com,b.com" precisa virar uma lista:

import os


def ler_bool(nome, padrao=False):
    valor = os.environ.get(nome)
    if valor is None:
        return padrao
    return valor.strip().lower() in ("1", "true", "sim", "yes")


def ler_lista(nome):
    valor = os.environ.get(nome, "")
    return [item.strip() for item in valor.split(",") if item.strip()]


# no servidor, quem define estas variáveis é o arquivo de ambiente (Passo 4)
os.environ["DJANGO_DEBUG"] = "False"
os.environ["DJANGO_ALLOWED_HOSTS"] = "meusite.com.br, www.meusite.com.br"

print("DEBUG:", ler_bool("DJANGO_DEBUG"))
print("ALLOWED_HOSTS:", ler_lista("DJANGO_ALLOWED_HOSTS"))
print("Variável que não existe:", ler_bool("NAO_EXISTE"), ler_lista("NAO_EXISTE"))

DEBUG: False
ALLOWED_HOSTS: ['meusite.com.br', 'www.meusite.com.br']
Variável que não existe: False []

Atenção: bool("False") dá True! Qualquer texto que não seja vazio é verdadeiro (aula 51). É por isso que existe a função ler_bool: um DEBUG = bool(os.environ["DJANGO_DEBUG"]) deixaria o modo de depuração ligado em produção.

Agora o trecho do config/settings.py que muda. Troque as linhas de SECRET_KEY, DEBUG, ALLOWED_HOSTS e DATABASES geradas pelo startproject por estas:

# config/settings.py (trecho)
import os
from pathlib import Path

BASE_DIR = Path(__file__).resolve().parent.parent

SECRET_KEY = os.environ["DJANGO_SECRET_KEY"]
DEBUG = os.environ.get("DJANGO_DEBUG", "False").lower() == "true"
ALLOWED_HOSTS = [h.strip() for h in os.environ.get("DJANGO_ALLOWED_HOSTS", "").split(",") if h.strip()]
CSRF_TRUSTED_ORIGINS = [f"https://{h}" for h in ALLOWED_HOSTS]

DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": os.environ.get("DB_NAME", "meusite"),
        "USER": os.environ.get("DB_USER", "meusite"),
        "PASSWORD": os.environ.get("DB_PASSWORD", ""),
        "HOST": os.environ.get("DB_HOST", "localhost"),
        "PORT": os.environ.get("DB_PORT", "5432"),
    }
}

STATIC_URL = "static/"
STATIC_ROOT = BASE_DIR / "staticfiles"
MEDIA_URL = "/media/"
MEDIA_ROOT = BASE_DIR / "media"

# segurança extra quando o site estiver com HTTPS
SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")
SECURE_SSL_REDIRECT = not DEBUG
SESSION_COOKIE_SECURE = not DEBUG
CSRF_COOKIE_SECURE = not DEBUG
SECURE_HSTS_SECONDS = 0 if DEBUG else 3600

(sem saída: com DJANGO_DEBUG=True e um banco local, o mesmo arquivo serve no seu computador)

  • os.environ["DJANGO_SECRET_KEY"] (com colchetes) dá erro se a variável faltar. Isso é bom: melhor o site nem ligar do que ligar com uma chave errada.
  • STATIC_ROOT é a pasta para onde o collectstatic copia o CSS e o JavaScript de todos os apps (inclusive os do admin), para o Nginx entregar.
  • SECURE_PROXY_SSL_HEADER avisa o Django de que o Nginx, na frente, já cuidou do HTTPS.
  • SECURE_HSTS_SECONDS pede ao navegador que só use HTTPS no seu site. Comece com um valor pequeno (1 hora) e aumente quando tudo estiver estável.

A SECRET_KEY assina as sessões e os tokens CSRF: quem a conhece pode se passar por qualquer usuário. Gere uma nova, forte, com o módulo secrets (aula 107):

import secrets

chave = secrets.token_urlsafe(50)
print("DJANGO_SECRET_KEY=" + chave)
print("Tamanho:", len(chave), "caracteres")

(exemplo — a sua saída pode ser diferente)
DJANGO_SECRET_KEY=-cLJx5OypV1HdT_tXtEpDTMwux7o0pTCJXcppay-Dmo8rvi1d2Bus7PLTKd7UPRxI7o
Tamanho: 67 caracteres

Por fim, liste os pacotes do projeto. O psycopg é o "tradutor" entre o Django e o PostgreSQL, e o gunicorn é o servidor:

pip install "psycopg[binary]" gunicorn
pip freeze > requirements.txt
git add .
git commit -m "Configurações de produção"
git push
Atenção: Confira que o .gitignore (aula 244) tem as linhas .env, .venv/, db.sqlite3, media/ e staticfiles/. Segredos e arquivos gerados não vão para o GitHub.

Passo 2: o servidor, o usuário e o firewall

O serviço de nuvem entrega o IP do servidor e o acesso como root, o usuário que pode tudo. Entre pelo SSH (o terminal remoto) e crie um usuário comum para o site, que só vira administrador com sudo quando precisa:

ssh root@203.0.113.10
adduser deploy
usermod -aG sudo deploy
exit
ssh deploy@203.0.113.10

Atualize o sistema, instale as peças e ligue o firewall ufw, deixando entrar só o SSH e o Nginx (portas 80 e 443):

sudo apt update && sudo apt upgrade -y
sudo apt install -y python3-venv python3-pip git postgresql nginx certbot python3-certbot-nginx
sudo ufw allow OpenSSH
sudo ufw allow "Nginx Full"
sudo ufw enable
sudo ufw status

Status: active
 
To                         Action      From
--                         ------      ----
OpenSSH                    ALLOW       Anywhere
Nginx Full                 ALLOW       Anywhere

Atenção: Libere o OpenSSH antes do ufw enable. Se ligar o firewall sem ele, a sua própria conexão SSH é bloqueada e você fica trancado do lado de fora do servidor.

Passo 3: o banco PostgreSQL

O PostgreSQL tem os próprios usuários. Entre no console dele como o administrador postgres e crie um usuário e um banco para o site (troque a senha por uma forte, gerada com secrets):

sudo -u postgres psql
CREATE USER meusite WITH PASSWORD 'troque-por-uma-senha-forte';
CREATE DATABASE meusite OWNER meusite;
\q

O banco só aceita conexões do próprio servidor (localhost) por padrão — exatamente o que queremos: o Django, rodando ali, conecta; a internet, não.

Passo 4: o código e as variáveis de ambiente

Baixe o projeto do GitHub, crie o ambiente virtual e instale os pacotes:

cd /home/deploy
git clone https://github.com/seu-usuario/meusite.git
cd meusite
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

Os segredos ficam num arquivo que só existe no servidor. Crie /home/deploy/meusite/.env (com nano .env) e depois deixe-o legível só pelo dono:

DJANGO_SECRET_KEY=cole-aqui-a-chave-gerada-no-passo-1
DJANGO_DEBUG=False
DJANGO_ALLOWED_HOSTS=meusite.com.br,www.meusite.com.br
DB_NAME=meusite
DB_USER=meusite
DB_PASSWORD=troque-por-uma-senha-forte
DB_HOST=localhost
DB_PORT=5432
chmod 600 .env
set -a; source .env; set +a
python manage.py migrate
python manage.py collectstatic --noinput
python manage.py createsuperuser

O set -a; source .env; set +a carrega as variáveis do arquivo no terminal atual, para os comandos do manage.py enxergarem os segredos. O collectstatic copia todos os arquivos estáticos para a pasta staticfiles/.

Passo 5: o Gunicorn como serviço

Teste primeiro na mão. O config.wsgi:application é o "ponto de entrada" que o startproject criou em config/wsgi.py:

gunicorn config.wsgi:application --bind 127.0.0.1:8000 --workers 3

[INFO] Starting gunicorn 23.0.0
[INFO] Listening at: http://127.0.0.1:8000
[INFO] Booting worker with pid: 4321

Funcionou? Aperte Ctrl+C. Agora peça ao systemd para cuidar dele. Crie o arquivo /etc/systemd/system/meusite.service (com sudo nano):

[Unit]
Description=Gunicorn do meusite
After=network.target

[Service]
User=deploy
Group=www-data
WorkingDirectory=/home/deploy/meusite
EnvironmentFile=/home/deploy/meusite/.env
ExecStart=/home/deploy/meusite/.venv/bin/gunicorn config.wsgi:application --bind 127.0.0.1:8000 --workers 3
Restart=always

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now meusite
sudo systemctl status meusite

● meusite.service - Gunicorn do meusite
     Active: active (running)

EnvironmentFile entrega as variáveis do .env ao Gunicorn; Restart=always religa o site se ele cair; enable faz ele ligar junto com o servidor. Se algo der errado, o diário do serviço mostra o erro: sudo journalctl -u meusite -n 50.

Passo 6: o Nginx na porta da frente

O Gunicorn escuta só em 127.0.0.1 (dentro do servidor). Quem atende a internet é o Nginx, que entrega os arquivos estáticos e de mídia direto do disco e repassa o resto ao Gunicorn — por isso ele é chamado de proxy reverso. Crie /etc/nginx/sites-available/meusite:

server {
    listen 80;
    server_name meusite.com.br www.meusite.com.br;

    client_max_body_size 10M;

    location /static/ {
        alias /home/deploy/meusite/staticfiles/;
    }

    location /media/ {
        alias /home/deploy/meusite/media/;
    }

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Ative o site, teste a configuração e recarregue o Nginx:

sudo ln -s /etc/nginx/sites-available/meusite /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl reload nginx

nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful

  • alias aponta a pasta do disco; a barra no fim dos dois lados (/static/ e staticfiles/) é obrigatória.
  • client_max_body_size 10M permite enviar imagens de até 10 MB (o padrão do Nginx é só 1 MB).
  • As linhas proxy_set_header contam ao Django o domínio pedido e se a conexão era HTTPS.

Por causa do SECURE_SSL_REDIRECT do Passo 1, até terminar o Passo 7 o Django manda todo visitante para o endereço https://, que ainda não existe. É normal o site "não abrir" agora; se quiser testar antes, ponha DJANGO_DEBUG=True no .env por alguns minutos e reinicie o serviço.

Dica: Se o Nginx não conseguir ler os arquivos estáticos (erro 403), dê permissão de passagem às pastas: chmod 755 /home/deploy.

Passo 7: HTTPS de graça com Certbot

O HTTPS criptografa a conversa entre o navegador e o servidor: sem ele, senhas e cookies passam "abertos" pela rede, e o navegador marca o site como "Não seguro". O Let's Encrypt dá certificados gratuitos, e o Certbot pede e instala o certificado no Nginx sozinho:

sudo certbot --nginx -d meusite.com.br -d www.meusite.com.br
sudo certbot renew --dry-run

Successfully deployed certificate for meusite.com.br
Congratulations! You have successfully enabled HTTPS on https://meusite.com.br

O certificado vale 90 dias, e o Certbot já deixa a renovação automática agendada; o --dry-run só testa se ela vai funcionar. O domínio precisa estar apontando para o IP do servidor antes deste passo.

Passo 8: a conferência final e as atualizações

O próprio Django tem uma lista de conferência de segurança. Rode no servidor, com as variáveis carregadas:

set -a; source .env; set +a
python manage.py check --deploy

WARNINGS:
?: (security.W005) You have not set the SECURE_HSTS_INCLUDE_SUBDOMAINS setting to True. ...
?: (security.W021) You have not set the SECURE_HSTS_PRELOAD setting to True. ...
 
System check identified 2 issues (0 silenced).

Cada aviso tem um código. Os dois acima não são falhas: eles perguntam se o HTTPS obrigatório deve valer também para os subdomínios e se o site deve entrar na lista de "só HTTPS" dos navegadores. Só ligue essas opções quando tiver certeza, porque desfazer leva meses. Já avisos como security.W018 (DEBUG ligado), security.W009 (SECRET_KEY fraca) ou security.W020 (ALLOWED_HOSTS vazio) precisam ser corrigidos antes de publicar.

Atenção: Nas versões mais novas do Django (6.1 em diante), o check --deploy também dá erro (mail.E001) se o envio de e-mail ainda estiver no modo de teste, que só escreve no terminal. Configure o envio por SMTP, como na aula 109, ou, se o site não manda e-mails, siga a dica que o próprio erro mostra.

A mesma ideia de "lista de conferência", em Python puro:

def conferir(config):
    problemas = []
    if config.get("DEBUG"):
        problemas.append("DEBUG está ligado: as páginas de erro mostram o seu código")
    if not config.get("ALLOWED_HOSTS"):
        problemas.append("ALLOWED_HOSTS vazio: o site responde 400 a todos")
    if len(config.get("SECRET_KEY", "")) < 50:
        problemas.append("SECRET_KEY curta ou ausente: gere uma com secrets")
    if not config.get("SESSION_COOKIE_SECURE"):
        problemas.append("cookie de sessão pode viajar sem HTTPS")
    return problemas


meu_computador = {"DEBUG": True, "ALLOWED_HOSTS": [], "SECRET_KEY": "django-insecure-abc"}
servidor = {"DEBUG": False, "ALLOWED_HOSTS": ["meusite.com.br"],
            "SECRET_KEY": "x" * 60, "SESSION_COOKIE_SECURE": True}

for nome, config in [("Meu computador", meu_computador), ("Servidor", servidor)]:
    problemas = conferir(config)
    print(f"{nome}: {len(problemas)} problema(s)")
    for p in problemas:
        print("  -", p)

Meu computador: 4 problema(s)
  - DEBUG está ligado: as páginas de erro mostram o seu código
  - ALLOWED_HOSTS vazio: o site responde 400 a todos
  - SECRET_KEY curta ou ausente: gere uma com secrets
  - cookie de sessão pode viajar sem HTTPS
Servidor: 0 problema(s)

Cada vez que você mudar o código no seu computador e der git push, atualize o servidor com esta sequência:

cd /home/deploy/meusite
git pull
source .venv/bin/activate
pip install -r requirements.txt
set -a; source .env; set +a

python manage.py check --deploy

Exercícios

1. Você publicou com DEBUG = False e todo o site responde 400 Bad Request. Qual configuração provavelmente está faltando, e como ela é preenchida no nosso settings?

Ver resposta

ALLOWED_HOSTS. Com DEBUG = False, o Django só atende os domínios dessa lista
e responde 400 a qualquer outro nome. No nosso settings ela vem da variável
DJANGO_ALLOWED_HOSTS do arquivo .env, por exemplo:
DJANGO_ALLOWED_HOSTS=meusite.com.br,www.meusite.com.br
Depois de corrigir: sudo systemctl restart meusite

2. Escreva a função ler_inteiro(nome, padrao) que lê uma variável de ambiente e converte para int, devolvendo o padrão quando ela não existe. Teste com DB_PORT.

Ver resposta 
import os


def ler_inteiro(nome, padrao):
    valor = os.environ.get(nome)
    if valor is None or not valor.strip():
        return padrao
    return int(valor)


print(ler_inteiro("DB_PORT", 5432))
os.environ["DB_PORT"] = "6543"
print(ler_inteiro("DB_PORT", 5432))

5432
6543

3. O site está no ar, mas sem nenhum CSS, e o admin aparece "pelado". O que você esqueceu de fazer ou de configurar?

Ver resposta

Os arquivos estáticos. Confira três coisas:
1. STATIC_ROOT no settings.py (BASE_DIR / "staticfiles");
2. rodar python manage.py collectstatic --noinput no servidor;
3. o bloco "location /static/ { alias /home/deploy/meusite/staticfiles/; }" no Nginx.
Com DEBUG = False o Django não serve mais o CSS: quem entrega é o Nginx.

4. O navegador mostra 502 Bad Gateway. O que isso significa e quais comandos ajudam a descobrir a causa?

Ver resposta 
sudo systemctl status meusite
sudo journalctl -u meusite -n 50

502 quer dizer que o Nginx está funcionando, mas não conseguiu falar com o Gunicorn atrás dele. Normalmente o Gunicorn não ligou por causa de um erro no código ou de uma variável faltando no .env (um KeyError: 'DJANGO_SECRET_KEY', por exemplo). O journalctl mostra o traceback.
