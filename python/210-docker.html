Para que serve o Docker

"Na minha máquina funciona!" — toda equipe já ouviu essa frase. O programa roda no seu computador, mas no do colega falta uma biblioteca, a versão do Python é outra, o banco não está instalado. O Docker resolve isso empacotando o programa com tudo de que ele precisa.

  • Uma imagem é esse pacote pronto: um mini sistema Linux com Python, as bibliotecas e o seu código. É como a receita congelada.
  • Um container é uma imagem rodando. Da mesma imagem saem quantos containers você quiser, todos iguais.
  • Um volume é uma pasta que sobrevive quando o container é apagado. É onde o banco guarda os dados.

Quem tiver Docker roda o projeto igualzinho, em qualquer computador — e no servidor também (aula 220).

Instalando e testando

No Windows, instale o Docker Desktop (docker.com), que usa o WSL2 (aula 240). No Linux, instale o pacote docker da sua distribuição; no macOS, o Docker Desktop também. Depois, no terminal:

docker --version
docker compose version
docker run --rm hello-world

Docker version 27.x.x
Docker Compose version v2.x.x
Hello from Docker!
This message shows that your installation appears to be working correctly.

O docker run baixou a imagem hello-world, criou um container, rodou e (por causa do --rm) apagou o container no fim.

O Dockerfile, linha por linha

O Dockerfile é a receita da imagem. Crie um arquivo chamado exatamente Dockerfile (sem extensão) na pasta do projeto, ao lado do manage.py:

# Dockerfile
FROM python:3.12-slim
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["python", "manage.py", "runserver", "0.0.0.0:8000"]
  • FROM — começa de uma imagem pronta com o Python 3.12 (a versão slim é menor);
  • ENV — não gravar arquivos .pyc e mostrar os print na hora, sem atraso;
  • WORKDIR /app — a pasta de trabalho dentro do container;
  • COPY requirements.txt . e RUN pip install — instala as bibliotecas;
  • COPY . . — copia o seu código;
  • CMD — o comando que roda quando o container começa.

Por que copiar o requirements.txt antes do resto? O Docker guarda cada passo em cache. Se você só mudou o código, ele reaproveita o passo do pip install e a imagem fica pronta em segundos.

O requirements.txt (aula 60) fica assim:

# requirements.txt
django>=5.0
psycopg[binary]>=3.1

O psycopg é o driver que deixa o Python conversar com o PostgreSQL. Crie também um .dockerignore, para não copiar lixo para dentro da imagem:

# .dockerignore
.venv/
__pycache__/
db.sqlite3
.env
.git/
Atenção: Dentro do container use 0.0.0.0:8000, nunca 127.0.0.1:8000. O 127.0.0.1 é "este computador" — e, dentro do container, "este computador" é o próprio container: o servidor só aceitaria conexões de dentro dele e o seu navegador não abriria a página.

Configurações nas variáveis de ambiente

A mesma imagem vai rodar no seu computador e no servidor, com senhas e bancos diferentes. Então o settings.py não pode ter nada disso escrito: ele lê das variáveis de ambiente (aulas 108 e 177), com um valor padrão para quando a variável não existe. Veja a ideia em Python puro (aqui definimos as variáveis no próprio código só para testar):

import os

os.environ["DJANGO_DEBUG"] = "0"
os.environ["DJANGO_ALLOWED_HOSTS"] = "localhost,agenda.exemplo.com"

DEBUG = os.environ.get("DJANGO_DEBUG", "1") == "1"
ALLOWED_HOSTS = os.environ.get("DJANGO_ALLOWED_HOSTS", "localhost").split(",")
SECRET_KEY = os.environ.get("DJANGO_SECRET_KEY", "so-para-desenvolvimento")

print("DEBUG:", DEBUG)
print("ALLOWED_HOSTS:", ALLOWED_HOSTS)
print("SECRET_KEY veio do ambiente?", "DJANGO_SECRET_KEY" in os.environ)

DEBUG: False
ALLOWED_HOSTS: ['localhost', 'agenda.exemplo.com']
SECRET_KEY veio do ambiente? False

Repare que toda variável de ambiente é texto: "0" não é False. Por isso comparamos com == "1". Um jeito prático de levar o endereço do banco é uma só variável, a DATABASE_URL, que o Python desmonta com urlsplit:

from urllib.parse import urlsplit

url = urlsplit("postgres://agenda:troque-esta-senha@db:5432/agenda")
print("Usuário:", url.username)
print("Senha:", url.password)
print("Servidor:", url.hostname)
print("Porta:", url.port)
print("Banco:", url.path.lstrip("/"))

Usuário: agenda
Senha: troque-esta-senha
Servidor: db
Porta: 5432
Banco: agenda

Com isso, dá para montar o dicionário DATABASES que o Django espera:

import os
from urllib.parse import urlsplit


def banco_da_url(texto):
    url = urlsplit(texto)
    if url.scheme == "sqlite":
        return {"ENGINE": "django.db.backends.sqlite3", "NAME": url.path.lstrip("/") or "db.sqlite3"}
    return {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": url.path.lstrip("/"),
        "USER": url.username,
        "PASSWORD": url.password,
        "HOST": url.hostname,
        "PORT": str(url.port or 5432),
    }


print(banco_da_url(os.environ.get("DATABASE_URL", "sqlite:///db.sqlite3")))
print(banco_da_url("postgres://agenda:segredo@db:5432/agenda"))

{'ENGINE': 'django.db.backends.sqlite3', 'NAME': 'db.sqlite3'}
{'ENGINE': 'django.db.backends.postgresql', 'NAME': 'agenda', 'USER': 'agenda', 'PASSWORD': 'segredo', 'HOST': 'db', 'PORT': '5432'}

Sem DATABASE_URL, o projeto usa o SQLite de sempre; no Docker, usa o PostgreSQL. No config/settings.py fica assim:

# config/settings.py (trecho)
import os
from urllib.parse import urlsplit

SECRET_KEY = os.environ.get("DJANGO_SECRET_KEY", "so-para-desenvolvimento")
DEBUG = os.environ.get("DJANGO_DEBUG", "1") == "1"
ALLOWED_HOSTS = os.environ.get("DJANGO_ALLOWED_HOSTS", "localhost,127.0.0.1").split(",")

_url = urlsplit(os.environ.get("DATABASE_URL", "sqlite:///db.sqlite3"))
if _url.scheme == "sqlite":
    DATABASES = {"default": {"ENGINE": "django.db.backends.sqlite3", "NAME": BASE_DIR / "db.sqlite3"}}
else:
    DATABASES = {"default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": _url.path.lstrip("/"),
        "USER": _url.username,
        "PASSWORD": _url.password,
        "HOST": _url.hostname,
        "PORT": str(_url.port or 5432),
    }}

python manage.py check

Docker Compose: vários containers juntos

Um site de verdade tem pelo menos duas peças: o Django e o banco. O Docker Compose descreve todas num arquivo só, compose.yaml, na pasta do projeto:

# compose.yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: agenda
      POSTGRES_USER: agenda
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    volumes:
      - dados_db:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U agenda"]
      interval: 3s
      retries: 10
  web:
    build: .
    ports:
      - "8000:8000"
    env_file: .env
    volumes:
      - .:/app
    depends_on:
      db:
        condition: service_healthy
volumes:
  dados_db:
  • db usa a imagem oficial do PostgreSQL; web é construído com o seu Dockerfile (build: .).
  • ports: "8000:8000" liga a porta 8000 do seu computador à 8000 do container.
  • Dentro do Compose, cada serviço é encontrado pelo nome: o Django acha o banco no endereço db.
  • volumes: - .:/app espelha a pasta do projeto dentro do container: você edita no VS Code e o runserver recarrega sozinho.
  • condition: service_healthy faz o Django esperar o banco estar pronto antes de começar.

As senhas ficam no arquivo .env, ao lado do compose.yaml (e fora do Git, aula 177):

# .env
POSTGRES_PASSWORD=troque-esta-senha
DATABASE_URL=postgres://agenda:troque-esta-senha@db:5432/agenda
DJANGO_SECRET_KEY=troque-por-um-texto-longo-e-aleatorio
DJANGO_DEBUG=1
Dica: O volume dados_db guarda os dados do banco fora do container: você pode parar, apagar e subir os containers de novo sem perder nenhum contato. Só o docker compose down -v (com -v) apaga o volume — use com cuidado.

Os comandos do dia a dia

docker compose up --build -d
docker compose ps
docker compose exec web python manage.py migrate
docker compose exec web python manage.py createsuperuser
docker compose logs -f web
docker compose down
  • up --build -d constrói a imagem e sobe tudo em segundo plano (-d);
  • ps mostra o que está rodando;
  • exec web ... roda um comando dentro do container web;
  • logs -f web acompanha as mensagens do Django (Ctrl+C para sair dos logs);
  • down para e apaga os containers (os volumes ficam).

NAME            IMAGE          SERVICE   STATUS                   PORTS
agenda-db-1     postgres:16    db        Up 20 seconds (healthy)  5432/tcp
agenda-web-1    agenda-web     web       Up 8 seconds             0.0.0.0:8000->8000/tcp

Agora abra http://127.0.0.1:8000/ no navegador: é a agenda da aula 207, rodando com PostgreSQL.

Atenção: Erro port is already allocated? Outro programa (talvez um runserver que você esqueceu aberto) já usa a porta 8000. Feche-o ou troque a linha para "8001:8000" e abra http://127.0.0.1:8001/.
Pratique no DIGITAR: digite este trecho no modo Programar do app. 
docker compose exec web python manage.py migrate

Exercícios

1. Qual comando cria um superusuário do Django rodando dentro do container web?

Ver resposta 
docker compose exec web python manage.py createsuperuser

2. Você acrescentou uma biblioteca no requirements.txt. O que precisa fazer para ela entrar no container, e por quê?

Ver resposta 
docker compose up --build -d

A imagem precisa ser reconstruída (--build), porque o pip install acontece na hora de construir a imagem, não quando o container começa.

3. Use urlsplit para desmontar postgres://loja:abc123@banco.exemplo.com:6543/vendas e mostre servidor, porta e nome do banco. Depois mostre que, numa URL sem porta, url.port é None.

Ver resposta 
from urllib.parse import urlsplit

url = urlsplit("postgres://loja:abc123@banco.exemplo.com:6543/vendas")
print(url.hostname, url.port, url.path.lstrip("/"))

sem_porta = urlsplit("postgres://loja:abc123@db/vendas")
print(sem_porta.port, sem_porta.port or 5432)

banco.exemplo.com 6543 vendas
None 5432

É por isso que a função banco_da_url usa url.port or 5432: a porta padrão do PostgreSQL.

4. Escreva uma função ler_bool(nome, padrao) que lê uma variável de ambiente e aceita "1", "true", "sim" e "yes" (maiúsculas ou minúsculas) como verdadeiro. Teste com DJANGO_DEBUG valendo "True", "0" e sem a variável.

Ver resposta 
import os


def ler_bool(nome, padrao=False):
    valor = os.environ.get(nome)
    if valor is None:
        return padrao
    return valor.strip().lower() in {"1", "true", "sim", "yes"}


os.environ["DJANGO_DEBUG"] = "True"
print(ler_bool("DJANGO_DEBUG"))
os.environ["DJANGO_DEBUG"] = "0"
print(ler_bool("DJANGO_DEBUG"))
del os.environ["DJANGO_DEBUG"]
print(ler_bool("DJANGO_DEBUG", padrao=True))

True
False
True

5. O container do Django sobe, os logs dizem Starting development server at http://127.0.0.1:8000/, mas o navegador não abre a página. Qual é o problema e como resolver?

Ver resposta

O runserver está ouvindo em 127.0.0.1, que dentro do container quer dizer "só o próprio container".
Troque no Dockerfile (ou no compose) para: python manage.py runserver 0.0.0.0:8000
e confira se o compose.yaml tem ports: "8000:8000". Depois: docker compose up --build

6. Para que serve o arquivo .dockerignore e por que o .env deve estar nele?

Ver resposta

O .dockerignore lista o que o COPY . . NÃO deve levar para dentro da imagem:
o .venv, o __pycache__, o banco de teste e o .git só deixam a imagem maior e mais lenta.
O .env tem senhas: se entrasse na imagem, qualquer pessoa com a imagem poderia lê-las.
As senhas chegam ao container pelo env_file do compose, na hora de rodar.
