Aula 211 · Projeto: blog (categorias, tags, slugs, imagens, context processors)

Nesta aula você vai aprender

  • Planejar os models de um blog ligando posts a categorias (ForeignKey) e tags (ManyToManyField)
  • Criar endereços amigáveis com SlugField, slugify e get_absolute_url
  • Enviar imagens de capa com ImageField e configurar MEDIA_URL e MEDIA_ROOT
  • Mostrar os posts em páginas com Paginator e filtrar por categoria e por tag
  • Colocar o menu de categorias em todas as páginas com um context processor
Aula para fazer no computador: o assunto desta aula precisa do seu computador. Os códigos sem o botão Executar devem ser copiados para um arquivo .py no VS Code e rodados no seu computador, como mostrado na aula 03.

O que vamos construir

Neste projeto você junta tudo o que viu nas aulas 200 a 207 num blog de verdade. Quem visita o site vê os últimos posts, de 5 em 5, clica num post para ler o texto inteiro e navega por categorias (Receitas, Viagens…) e por tags (#doce, #praia…). Quem escreve usa a área administrativa.

O blog terá estes endereços:

  • / — lista dos posts publicados, com páginas (/?pagina=2);
  • /post/pao-de-queijo-mineiro/ — um post, achado pelo slug (o título escrito do jeito que cabe numa URL);
  • /categoria/receitas/ e /tag/doce/ — só os posts daquela categoria ou tag;
  • /admin/ — onde você escreve, publica e envia as imagens.

Cada post pertence a uma categoria, mas uma categoria tem muitos posts: isso é uma ForeignKey. Já as tags são "muitos para muitos": um post tem várias tags e uma tag aparece em vários posts. Isso é um ManyToManyField, que por baixo dos panos cria uma tabela de ligação, como na aula 173.

Passo 2: entendendo o slug

Um título como "Pão de queijo mineiro!" tem acentos, espaços e pontuação, que ficam feios (ou quebram) numa URL. O slug é a versão "limpa": só letras minúsculas sem acento, números e hífens. O Django já tem a função slugify, mas vale entender o que ela faz. Esta versão feita à mão roda aqui no navegador:

import re
import unicodedata


def meu_slugify(texto):
    # separa a letra do acento (á -> a + ´) e joga fora o que não é ASCII
    sem_acento = unicodedata.normalize("NFKD", texto).encode("ascii", "ignore").decode()
    # tudo que não for letra ou número vira um hífen
    com_hifens = re.sub(r"[^a-z0-9]+", "-", sem_acento.lower())
    return com_hifens.strip("-")


print(meu_slugify("Olá, Mundo!"))
print(meu_slugify("Pão de queijo mineiro!"))
print(meu_slugify("10 dicas de digitação"))

ola-mundo
pao-de-queijo-mineiro
10-dicas-de-digitacao

O slug precisa ser único: dois posts com o mesmo endereço seriam um problema. A saída é acrescentar um número quando o slug já existe. Veja a ideia com um conjunto (set, aula 48) no papel do banco de dados:

import re
import unicodedata


def meu_slugify(texto):
    sem_acento = unicodedata.normalize("NFKD", texto).encode("ascii", "ignore").decode()
    return re.sub(r"[^a-z0-9]+", "-", sem_acento.lower()).strip("-")


def slug_unico(titulo, existentes):
    base = meu_slugify(titulo)
    slug = base
    numero = 2
    while slug in existentes:
        slug = f"{base}-{numero}"
        numero += 1
    return slug


banco = set()
for titulo in ["Bolo de cenoura", "Bolo de cenoura", "Bolo de Cenoura!"]:
    slug = slug_unico(titulo, banco)
    banco.add(slug)
    print(slug)

bolo-de-cenoura
bolo-de-cenoura-2
bolo-de-cenoura-3

É exatamente isso que o model Post vai fazer no método save, só que perguntando ao banco com Post.objects.filter(slug=slug).exists().

Passo 3: os models

Escreva o arquivo inteiro blog/models.py:

# blog/models.py
from django.db import models
from django.urls import reverse
from django.utils.text import slugify


class Categoria(models.Model):
    nome = models.CharField(max_length=60)
    slug = models.SlugField(unique=True)

    class Meta:
        ordering = ["nome"]

    def __str__(self):
        return self.nome

    def get_absolute_url(self):
        return reverse("categoria", args=[self.slug])


class Tag(models.Model):
    nome = models.CharField(max_length=40, unique=True)
    slug = models.SlugField(unique=True)

    def __str__(self):
        return self.nome

    def get_absolute_url(self):
        return reverse("tag", args=[self.slug])


class Post(models.Model):
    titulo = models.CharField(max_length=150)
    slug = models.SlugField(max_length=160, unique=True, blank=True)
    categoria = models.ForeignKey(Categoria, on_delete=models.PROTECT, related_name="posts")
    tags = models.ManyToManyField(Tag, blank=True, related_name="posts")
    capa = models.ImageField(upload_to="capas/", blank=True)
    resumo = models.CharField(max_length=200)
    texto = models.TextField()
    publicado = models.BooleanField(default=False)
    criado_em = models.DateTimeField(auto_now_add=True)

    class Meta:
        ordering = ["-criado_em"]

    def __str__(self):
        return self.titulo

    def save(self, *args, **kwargs):
        if not self.slug:
            base = slugify(self.titulo)
            slug = base
            numero = 2
            while Post.objects.filter(slug=slug).exists():
                slug = f"{base}-{numero}"
                numero += 1
            self.slug = slug
        super().save(*args, **kwargs)

    def get_absolute_url(self):
        return reverse("post", args=[self.slug])

(sem saída: os models descrevem as tabelas)

O que tem de novo aqui:

  • on_delete=models.PROTECT impede apagar uma categoria que ainda tem posts. Assim nenhum post fica "órfão" sem querer.
  • related_name="posts" dá o caminho de volta: categoria.posts.all() e tag.posts.all() trazem os posts dela.
  • get_absolute_url devolve o endereço do objeto. Nos templates basta escrever {{ post.get_absolute_url }}, e se um dia a URL mudar, você só altera o urls.py.
  • ordering = ["-criado_em"] deixa os posts mais novos primeiro (o - inverte a ordem).

Passo 5: imagens de capa

Arquivos enviados pelos usuários (as capas) são chamados de mídia e ficam separados dos arquivos estáticos do site (CSS, logo). Diga ao Django onde guardá-los, no fim do config/settings.py:

# config/settings.py (trecho, no fim do arquivo)
MEDIA_URL = "/media/"
MEDIA_ROOT = BASE_DIR / "media"

(as capas enviadas vão parar em media/capas/)

  • MEDIA_ROOT é a pasta do computador onde os arquivos são gravados;
  • MEDIA_URL é o começo do endereço usado para mostrar esses arquivos no navegador.

Durante o desenvolvimento, o runserver precisa saber servir essa pasta. Escreva o config/urls.py inteiro:

# config/urls.py
from django.conf import settings
from django.conf.urls.static import static
from django.contrib import admin
from django.urls import include, path

urlpatterns = [
    path("admin/", admin.site.urls),
    path("", include("blog.urls")),
]

if settings.DEBUG:
    urlpatterns += static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT)

(uma capa enviada abre em http://127.0.0.1:8000/media/capas/nome-da-imagem.jpg)

Dica: Se um dia você fizer um formulário próprio de envio de imagem (fora do admin), a tag precisa ser <form method="post" enctype="multipart/form-data"> e a view tem de passar request.FILES para o form. Sem isso, o texto chega e a imagem não.

Passo 6: as views e as URLs

O Paginator (aula 204) divide uma lista em páginas. Antes de usá-lo, veja a conta que ele faz, com fatias de lista (aula 20):

import math


def paginar(itens, por_pagina, numero):
    total_paginas = max(1, math.ceil(len(itens) / por_pagina))
    numero = min(max(1, numero), total_paginas)   # página inválida vira a mais próxima
    inicio = (numero - 1) * por_pagina
    return itens[inicio:inicio + por_pagina], numero, total_paginas


posts = [f"Post {n}" for n in range(1, 13)]
for pedido in [1, 3, 99]:
    pagina, numero, total = paginar(posts, 5, pedido)
    print(f"Página {numero} de {total}: {pagina}")

Página 1 de 3: ['Post 1', 'Post 2', 'Post 3', 'Post 4', 'Post 5']
Página 3 de 3: ['Post 11', 'Post 12']
Página 3 de 3: ['Post 11', 'Post 12']

O get_page do Django faz igualzinho: se alguém digitar ?pagina=99 ou ?pagina=abc, ele mostra uma página válida em vez de dar erro. Agora escreva blog/views.py:

# blog/views.py
from django.core.paginator import Paginator
from django.shortcuts import get_object_or_404, render
from .models import Categoria, Post, Tag


def paginar(request, posts):
    paginador = Paginator(posts, 5)
    return paginador.get_page(request.GET.get("pagina"))


def lista(request):
    posts = Post.objects.filter(publicado=True)
    contexto = {"titulo": "Últimos posts", "pagina": paginar(request, posts)}
    return render(request, "blog/lista.html", contexto)


def por_categoria(request, slug):
    categoria = get_object_or_404(Categoria, slug=slug)
    posts = categoria.posts.filter(publicado=True)
    contexto = {"titulo": f"Categoria: {categoria.nome}", "pagina": paginar(request, posts)}
    return render(request, "blog/lista.html", contexto)


def por_tag(request, slug):
    tag = get_object_or_404(Tag, slug=slug)
    posts = tag.posts.filter(publicado=True)
    contexto = {"titulo": f"Tag: {tag.nome}", "pagina": paginar(request, posts)}
    return render(request, "blog/lista.html", contexto)


def post(request, slug):
    item = get_object_or_404(Post, slug=slug, publicado=True)
    return render(request, "blog/post.html", {"post": item})

(sem saída: as views só rodam quando alguém abre uma página)

Repare que as três listas usam o mesmo template, blog/lista.html; só o título e os posts mudam. E a view post exige publicado=True: um rascunho dá "página não encontrada" (404) para quem tentar adivinhar o endereço.

Crie o arquivo blog/urls.py:

# blog/urls.py
from django.urls import path
from . import views

urlpatterns = [
    path("", views.lista, name="lista"),
    path("post/<slug:slug>/", views.post, name="post"),
    path("categoria/<slug:slug>/", views.por_categoria, name="categoria"),
    path("tag/<slug:slug>/", views.por_tag, name="tag"),
]

(o conversor <slug:slug> aceita só letras, números, hífens e sublinhados)

Passo 7: o menu em todas as páginas

O menu do topo lista todas as categorias. Toda view teria de mandar Categoria.objects.all() no contexto… e um dia alguém esqueceria. O context processor resolve: é uma função que recebe o request e devolve um dicionário que o Django junta ao contexto de todos os templates. A ideia, em Python puro:

def categorias(request):
    return {"menu_categorias": ["Receitas", "Viagens"]}


def usuario(request):
    return {"usuario": request["usuario"]}


processadores = [categorias, usuario]


def montar_contexto(request, contexto_da_view):
    contexto = {}
    for funcao in processadores:
        contexto.update(funcao(request))
    contexto.update(contexto_da_view)
    return contexto


pedido = {"usuario": "Bia"}
print(montar_contexto(pedido, {"titulo": "Últimos posts"}))
print(montar_contexto(pedido, {"titulo": "Tag: doce"}))

{'menu_categorias': ['Receitas', 'Viagens'], 'usuario': 'Bia', 'titulo': 'Últimos posts'}
{'menu_categorias': ['Receitas', 'Viagens'], 'usuario': 'Bia', 'titulo': 'Tag: doce'}

Agora a versão de verdade. Crie blog/context_processors.py:

# blog/context_processors.py
from .models import Categoria


def categorias(request):
    return {"menu_categorias": Categoria.objects.all()}

(todo template passa a enxergar a variável menu_categorias)

E registre a função em config/settings.py, dentro de TEMPLATES:

# config/settings.py (trecho)
TEMPLATES = [
    {
        "BACKEND": "django.template.backends.django.DjangoTemplates",
        "DIRS": [],
        "APP_DIRS": True,
        "OPTIONS": {
            "context_processors": [
                "django.template.context_processors.request",
                "django.contrib.auth.context_processors.auth",
                "django.contrib.messages.context_processors.messages",
                "blog.context_processors.categorias",
            ],
        },
    },
]

(a última linha é a única novidade)

Atenção: O caminho no settings.py é texto: "blog.context_processors.categorias". Um erro de digitação ali só aparece quando uma página é aberta, como ModuleNotFoundError ou AttributeError. Se o site inteiro quebrar logo depois desse passo, confira essa linha.

def resumir(texto, palavras):
    lista = texto.split()
    if len(lista) <= palavras:
        return texto
    return " ".join(lista[:palavras]) + "..."

3. Acrescente uma busca ao blog: a view busca lê ?q= e mostra os posts publicados com o termo no título ou no texto, usando o template blog/lista.html.

# blog/views.py (acrescente)
from django.db.models import Q


def busca(request):
    termo = request.GET.get("q", "")
    posts = Post.objects.filter(publicado=True).filter(
        Q(titulo__icontains=termo) | Q(texto__icontains=termo)
    )
    contexto = {"titulo": f"Busca: {termo}", "pagina": paginar(request, posts)}
    return render(request, "blog/lista.html", contexto)

Ver resposta 
# blog/context_processors.py
from django.db.models import Count, Q
from .models import Categoria


def categorias(request):
    menu = Categoria.objects.annotate(
        total=Count("posts", filter=Q(posts__publicado=True))
    )
    return {"menu_categorias": menu}

No base.html, troque o texto do link por {{ cat.nome }} ({{ cat.total }}). O annotate com Count pede ao banco a contagem numa única consulta, em vez de uma consulta por categoria.

6. Por que a ForeignKey da categoria usa on_delete=models.PROTECT e não models.CASCADE?

Ver resposta

Com CASCADE, apagar a categoria "Receitas" apagaria junto TODOS os posts dela, sem aviso.
Com PROTECT, o Django recusa apagar a categoria enquanto houver posts nela
(dá ProtectedError, e o admin mostra quais posts impedem). Primeiro você move
ou apaga os posts, depois a categoria. É uma proteção contra perder textos sem querer.
