Para que servem os padrões comportamentais

Os padrões comportamentais cuidam de quem faz o quê e de como os objetos conversam. Eles evitam dois problemas comuns: funções gigantes cheias de if que tentam decidir tudo, e objetos que precisam conhecer todos os outros.

São dez padrões nesta aula. Você não precisa decorar todos de uma vez: leia o problema de cada um e guarde o nome. Quando o problema aparecer no seu código, você vai lembrar que existe uma solução pronta.

Strategy: trocar o algoritmo

Problema: há vários jeitos de fazer a mesma tarefa (calcular frete, ordenar uma lista, a jogada do computador num jogo) e você quer escolher na hora, sem uma fila de if.

A Strategy guarda o "jeito de fazer" num objeto separado. Em Python, uma função já serve como estratégia, porque funções são valores (aula 45):

def ataque_agressivo(vida_inimigo):
    return 30


def ataque_cauteloso(vida_inimigo):
    return 10


def ataque_esperto(vida_inimigo):
    return 50 if vida_inimigo <= 50 else 15


def lutar(estrategia, vida=100):
    turnos = 0
    while vida > 0:
        vida -= estrategia(vida)
        turnos += 1
    return turnos


for estrategia in [ataque_agressivo, ataque_cauteloso, ataque_esperto]:
    print(f"{estrategia.__name__:<17} venceu em {lutar(estrategia)} turnos")

ataque_agressivo  venceu em 4 turnos
ataque_cauteloso  venceu em 10 turnos
ataque_esperto    venceu em 5 turnos

Você já usou Strategy sem saber: em sorted(lista, key=len), a função key é a estratégia de ordenação (aula 49).

Dica: Use classes como estratégia só quando cada estratégia precisa guardar dados ou ter vários métodos. Para "um jeito de calcular", uma função basta.

Observer: avisar quem se interessa

Problema: quando algo acontece (um vídeo novo no canal, um gol, a temperatura subir), várias partes do programa querem saber. Se o canal tivesse de conhecer cada inscrito pelo nome, adicionar um inscrito novo obrigaria a mudar o canal.

No Observer, o objeto observado guarda uma lista de interessados e avisa todos quando algo muda. Os interessados se inscrevem e saem quando quiserem:

class Canal:
    def __init__(self, nome):
        self.nome = nome
        self.inscritos = []

    def inscrever(self, funcao):
        self.inscritos.append(funcao)

    def cancelar(self, funcao):
        self.inscritos.remove(funcao)

    def publicar(self, video):
        print(f"[{self.nome}] novo vídeo: {video}")
        for avisar in self.inscritos:
            avisar(self.nome, video)


def notificacao_celular(canal, video):
    print(f"  celular: {canal} postou '{video}'")


def email(canal, video):
    print(f"  e-mail: assista '{video}'")


canal = Canal("Ciência Divertida")
canal.inscrever(notificacao_celular)
canal.inscrever(email)
canal.publicar("Vulcão de bicarbonato")
canal.cancelar(email)
canal.publicar("Foguete de garrafa PET")

[Ciência Divertida] novo vídeo: Vulcão de bicarbonato
  celular: Ciência Divertida postou 'Vulcão de bicarbonato'
  e-mail: assista 'Vulcão de bicarbonato'
[Ciência Divertida] novo vídeo: Foguete de garrafa PET
  celular: Ciência Divertida postou 'Foguete de garrafa PET'

Os botões das janelas (aula 192, sinais e slots) funcionam assim: o botão avisa todas as funções ligadas ao clicked.

Command: a ação vira objeto (e dá para desfazer)

Problema: você quer guardar ações para fazer depois, repetir ou desfazer (o famoso Ctrl+Z). Se a ação for só uma linha de código executada na hora, ela some.

No Command, cada ação vira um objeto com executar() e desfazer(). O programa guarda uma pilha com as ações feitas:

class Editor:
    def __init__(self):
        self.texto = ""


class Escrever:
    def __init__(self, editor, trecho):
        self.editor = editor
        self.trecho = trecho

    def executar(self):
        self.editor.texto += self.trecho

    def desfazer(self):
        self.editor.texto = self.editor.texto[:-len(self.trecho)]


class Historico:
    def __init__(self):
        self.feitos = []

    def fazer(self, comando):
        comando.executar()
        self.feitos.append(comando)

    def desfazer(self):
        if self.feitos:
            self.feitos.pop().desfazer()


ed = Editor()
h = Historico()
h.fazer(Escrever(ed, "Olá"))
h.fazer(Escrever(ed, ", mundo"))
h.fazer(Escrever(ed, "!!!"))
print(repr(ed.texto))
h.desfazer()
print(repr(ed.texto))
h.desfazer()
print(repr(ed.texto))

'Olá, mundo!!!'
'Olá, mundo'
'Olá'

A lista feitos funciona como uma pilha: o último a entrar é o primeiro a sair (aula 117).

State: o comportamento muda com o estado

Problema: um objeto age diferente conforme a situação. Um semáforo verde, amarelo e vermelho; um personagem andando, pulando ou caído. Com if estado == ... espalhados por todos os métodos, o código vira uma bagunça.

No State, cada estado é um objeto que sabe o que fazer e qual é o próximo estado:

class Verde:
    def proximo(self):
        return Amarelo()

    def pode_passar(self):
        return True


class Amarelo:
    def proximo(self):
        return Vermelho()

    def pode_passar(self):
        return False


class Vermelho:
    def proximo(self):
        return Verde()

    def pode_passar(self):
        return False


class Semaforo:
    def __init__(self):
        self.estado = Vermelho()

    def trocar(self):
        self.estado = self.estado.proximo()


s = Semaforo()
for _ in range(4):
    s.trocar()
    nome = type(s.estado).__name__
    print(f"{nome:<8} pode passar? {s.estado.pode_passar()}")

Verde    pode passar? True
Amarelo  pode passar? False
Vermelho pode passar? False
Verde    pode passar? True

Para criar um estado novo (pisca-alerta), você escreve uma classe e muda só quem aponta para ela.

Template Method: o roteiro fixo

Problema: várias tarefas seguem o mesmo roteiro, mudando só alguns passos. Toda receita de bolo é: preparar a massa, assar, decorar. Copiar o roteiro em cada classe espalha a mesma lógica em vários lugares.

No Template Method, a classe mãe define o roteiro e as filhas preenchem os passos que mudam:

class Bolo:
    def fazer(self):                     # o "método modelo"
        print(f"--- {type(self).__name__} ---")
        self.massa()
        print("Assar por 40 minutos")
        self.cobertura()

    def massa(self):
        print("Massa básica: farinha, ovos, leite")

    def cobertura(self):
        print("Sem cobertura")


class BoloDeCenoura(Bolo):
    def massa(self):
        print("Massa com cenoura batida")

    def cobertura(self):
        print("Cobertura de chocolate")


class BoloSimples(Bolo):
    pass


BoloDeCenoura().fazer()
BoloSimples().fazer()

--- BoloDeCenoura ---
Massa com cenoura batida
Assar por 40 minutos
Cobertura de chocolate
--- BoloSimples ---
Massa básica: farinha, ovos, leite
Assar por 40 minutos
Sem cobertura

O unittest (aula 131) usa esse padrão: ele chama setUp, depois o teste, depois tearDown; você só preenche os passos.

Iterator: percorrer sem expor o miolo

Problema: você quer percorrer uma coleção com for sem que quem usa precise saber como ela é guardada por dentro (lista, árvore, páginas de um livro).

O Iterator já faz parte do Python: todo objeto com __iter__ funciona no for (aulas 52 e 90). Um gerador com yield é o jeito mais curto de escrever um:

class Playlist:
    def __init__(self, *musicas):
        self._musicas = list(musicas)

    def __iter__(self):
        yield from self._musicas

    def embaralhada(self, semente):
        import random
        ordem = self._musicas[:]
        random.Random(semente).shuffle(ordem)
        yield from ordem


p = Playlist("Aquarela", "Trem das Onze", "País Tropical", "Sina")
for m in p:
    print("tocando:", m)
print(list(p.embaralhada(semente=7)))

tocando: Aquarela
tocando: Trem das Onze
tocando: País Tropical
tocando: Sina
['Sina', 'Trem das Onze', 'Aquarela', 'País Tropical']

Repare que a mesma playlist oferece dois jeitos de percorrer, e a lista _musicas continua escondida.

Chain of Responsibility: passar adiante

Problema: um pedido pode ser tratado por várias pessoas em sequência, e cada uma decide se resolve ou passa para a próxima. No suporte de um jogo: o robô responde dúvidas simples, o atendente resolve problemas de conta e o gerente cuida de reembolsos.

Cada "elo" da corrente tenta tratar o pedido; se não for com ele, repassa:

class Atendente:
    def __init__(self, proximo=None):
        self.proximo = proximo

    def tratar(self, pedido):
        if self.consegue(pedido):
            return f"{type(self).__name__} resolveu: {pedido}"
        if self.proximo:
            return self.proximo.tratar(pedido)
        return f"Ninguém resolveu: {pedido}"


class Robo(Atendente):
    def consegue(self, pedido):
        return "senha" in pedido


class Suporte(Atendente):
    def consegue(self, pedido):
        return "conta" in pedido


class Gerente(Atendente):
    def consegue(self, pedido):
        return "reembolso" in pedido


corrente = Robo(Suporte(Gerente()))
for pedido in ["esqueci a senha", "conta bloqueada", "quero reembolso", "jogo travou"]:
    print(corrente.tratar(pedido))

Robo resolveu: esqueci a senha
Suporte resolveu: conta bloqueada
Gerente resolveu: quero reembolso
Ninguém resolveu: jogo travou

É o mesmo jeito que funcionam os except em sequência (aula 53) e os "middlewares" do Django: cada um olha o pedido e decide se age.

Mediator: um centro que coordena

Problema: muitos objetos precisam conversar entre si. Se cada um conhece todos os outros, as ligações viram um emaranhado. Numa sala de bate-papo, imagine cada aluno guardando a lista de todos os colegas.

O mediador fica no meio: cada objeto conversa só com ele, e ele repassa para quem precisa — como a torre de controle de um aeroporto:

class SalaDeBatePapo:
    def __init__(self):
        self.membros = {}

    def entrar(self, aluno):
        self.membros[aluno.nome] = aluno
        aluno.sala = self

    def enviar(self, de, texto, para=None):
        for nome, aluno in self.membros.items():
            if nome != de and (para is None or nome == para):
                aluno.receber(de, texto)


class Aluno:
    def __init__(self, nome):
        self.nome = nome
        self.sala = None

    def falar(self, texto, para=None):
        self.sala.enviar(self.nome, texto, para)

    def receber(self, de, texto):
        print(f"{self.nome} recebeu de {de}: {texto}")


sala = SalaDeBatePapo()
ana, bia, caio = Aluno("Ana"), Aluno("Bia"), Aluno("Caio")
for a in (ana, bia, caio):
    sala.entrar(a)
ana.falar("Alguém fez a lição?")
caio.falar("Fiz! Te mando.", para="Ana")

Bia recebeu de Ana: Alguém fez a lição?
Caio recebeu de Ana: Alguém fez a lição?
Ana recebeu de Caio: Fiz! Te mando.

Nenhum aluno conhece os outros; todos conhecem só a sala.

Memento: salvar e voltar

Problema: você quer "salvar o jogo" e poder voltar para aquele ponto depois, sem deixar o resto do programa mexer nos detalhes internos do personagem.

O Memento é uma fotografia do estado. O próprio objeto cria a foto e sabe restaurá-la; quem guarda as fotos (o "zelador") não mexe nelas:

from dataclasses import dataclass


@dataclass(frozen=True)
class SaveGame:                 # o memento: não pode ser alterado
    fase: int
    vida: int
    itens: tuple


class Jogador:
    def __init__(self):
        self.fase, self.vida, self.itens = 1, 100, []

    def salvar(self):
        return SaveGame(self.fase, self.vida, tuple(self.itens))

    def carregar(self, save):
        self.fase, self.vida, self.itens = save.fase, save.vida, list(save.itens)

    def __repr__(self):
        return f"fase {self.fase}, vida {self.vida}, itens {self.itens}"


j = Jogador()
j.fase, j.itens = 3, ["chave"]
saves = [j.salvar()]                    # o zelador: só guarda
j.vida, j.itens = 10, []                # caiu numa armadilha...
print("Agora:", j)
j.carregar(saves[-1])
print("Depois de carregar:", j)

Agora: fase 3, vida 10, itens []
Depois de carregar: fase 3, vida 100, itens ['chave']

Command e Memento combinam bem: um editor pode guardar um memento antes de cada comando e usá-lo para desfazer.

Visitor: operações novas sem mexer nas classes

Problema: você tem várias classes (Círculo, Retângulo, Triângulo) e quer criar operações novas sobre elas — calcular área, desenhar, exportar — sem encher cada classe de métodos.

No Visitor, cada operação vira um objeto "visitante" com um método para cada tipo. As formas só sabem "receber a visita":

class Circulo:
    def __init__(self, raio):
        self.raio = raio

    def aceitar(self, visitante):
        return visitante.visitar_circulo(self)


class Retangulo:
    def __init__(self, largura, altura):
        self.largura, self.altura = largura, altura

    def aceitar(self, visitante):
        return visitante.visitar_retangulo(self)


class CalculaArea:
    def visitar_circulo(self, c):
        return round(3.14159 * c.raio ** 2, 2)

    def visitar_retangulo(self, r):
        return r.largura * r.altura


class Descreve:
    def visitar_circulo(self, c):
        return f"círculo de raio {c.raio}"

    def visitar_retangulo(self, r):
        return f"retângulo {r.largura}x{r.altura}"


formas = [Circulo(2), Retangulo(3, 4)]
for f in formas:
    print(f.aceitar(Descreve()), "-> área", f.aceitar(CalculaArea()))

círculo de raio 2 -> área 12.57
retângulo 3x4 -> área 12

Em Python moderno, o match/case (aula 92) faz um trabalho parecido de um jeito mais curto, escolhendo o código pelo tipo do objeto:

from dataclasses import dataclass


@dataclass
class Circulo:
    raio: float


@dataclass
class Retangulo:
    largura: float
    altura: float


def perimetro(forma):
    match forma:
        case Circulo(raio=r):
            return round(2 * 3.14159 * r, 2)
        case Retangulo(largura=l, altura=a):
            return 2 * (l + a)


for f in [Circulo(1), Retangulo(3, 4)]:
    print(f, "-> perímetro", perimetro(f))

Circulo(raio=1) -> perímetro 6.28
Retangulo(largura=3, altura=4) -> perímetro 14

Resumo e cuidados

  • Strategy: trocar o jeito de fazer (em Python, muitas vezes uma função).
  • Observer: avisar vários interessados quando algo muda.
  • Command: transformar ações em objetos para guardar, repetir e desfazer.
  • State: cada estado é um objeto que sabe agir e qual é o próximo.
  • Template Method: a mãe fixa o roteiro, as filhas preenchem os passos.
  • Iterator: percorrer com for sem mostrar o miolo (__iter__, yield).
  • Chain of Responsibility: passar o pedido adiante até alguém resolver.
  • Mediator: um centro que coordena a conversa entre muitos objetos.
  • Memento: fotografia do estado para voltar depois.
  • Visitor: operações novas sobre várias classes sem mexer nelas (ou match/case).
Atenção: Um erro comum no Observer é esquecer de cancelar a inscrição: o objeto observado continua guardando a função e chamando-a para sempre, mesmo quando quem se inscreveu nem existe mais na tela.
Atenção: Padrão não é enfeite. Se uma simples função com um if resolve e é fácil de ler, ela é a melhor solução. Os padrões valem a pena quando os casos crescem ou mudam com frequência.

4. Use Chain of Responsibility para validar uma senha: os elos Tamanho (pelo menos 8 caracteres), TemNumero e TemMaiuscula. Cada elo devolve a mensagem de erro ou passa adiante; no fim da corrente, a senha está aprovada. Teste com "abc", "abcdefgh", "abcdefg1" e "Abcdefg1".

Ver resposta 
class Regra:
    def __init__(self, proximo=None):
        self.proximo = proximo

    def checar(self, senha):
        erro = self.erro(senha)
        if erro:
            return erro
        return self.proximo.checar(senha) if self.proximo else "senha aprovada"


class Tamanho(Regra):
    def erro(self, senha):
        return "curta demais" if len(senha) < 8 else None


class TemNumero(Regra):
    def erro(self, senha):
        return None if any(c.isdigit() for c in senha) else "falta um número"


class TemMaiuscula(Regra):
    def erro(self, senha):
        return None if any(c.isupper() for c in senha) else "falta uma maiúscula"


validador = Tamanho(TemNumero(TemMaiuscula()))
for s in ["abc", "abcdefgh", "abcdefg1", "Abcdefg1"]:
    print(f"{s:<9} -> {validador.checar(s)}")

abc       -> curta demais
abcdefgh  -> falta um número
abcdefg1  -> falta uma maiúscula
Abcdefg1  -> senha aprovada
