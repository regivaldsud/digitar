O que é um padrão de projeto

Muitos problemas de programação se repetem em projetos diferentes. Um padrão de projeto é uma solução já testada para um desses problemas, com um nome que todo programador entende. Em 1994, quatro autores (apelidados de "Gangue dos Quatro", GoF) catalogaram 23 padrões em três grupos:

  • criacionais — como os objetos são criados (esta aula);
  • estruturais — como os objetos se encaixam (aula 152);
  • comportamentais — como os objetos conversam (aula 153).

O livro foi escrito pensando em linguagens como C++ e Java. Em Python, vários padrões ficam bem mais curtos, porque funções, classes e módulos também são objetos. Nesta aula você vê a ideia de cada um e a versão pythônica.

Factory Method: um lugar só para escolher a classe

Problema: o programa precisa criar objetos de classes diferentes conforme uma informação (um texto do arquivo, uma opção do menu). Se cada parte do código fizer seu próprio if para escolher a classe, ao surgir uma classe nova você precisa caçar todos esses if.

A fábrica concentra essa escolha num único lugar:

class Cachorro:
    def falar(self):
        return "Au au"


class Gato:
    def falar(self):
        return "Miau"


class Vaca:
    def falar(self):
        return "Muuu"


ANIMAIS = {"cachorro": Cachorro, "gato": Gato, "vaca": Vaca}


def criar_animal(tipo):
    try:
        return ANIMAIS[tipo]()
    except KeyError:
        raise ValueError(f"animal desconhecido: {tipo}") from None


for nome in ["gato", "vaca", "cachorro"]:
    print(nome, "->", criar_animal(nome).falar())

gato -> Miau
vaca -> Muuu
cachorro -> Au au

Em Python, uma classe é um valor como outro qualquer: dá para guardá-la num dicionário e chamá-la depois. Por isso a fábrica pythônica muitas vezes é só um dicionário e uma função.

Na forma clássica do livro, o "método fábrica" fica numa classe mãe, e cada filha decide o que criar:

class Fase:
    def criar_inimigo(self):          # o "Factory Method"
        raise NotImplementedError

    def iniciar(self):
        inimigo = self.criar_inimigo()
        print(f"{type(self).__name__}: apareceu um {inimigo}!")


class FaseFloresta(Fase):
    def criar_inimigo(self):
        return "lobo"


class FaseCastelo(Fase):
    def criar_inimigo(self):
        return "dragão"


for fase in [FaseFloresta(), FaseCastelo()]:
    fase.iniciar()

FaseFloresta: apareceu um lobo!
FaseCastelo: apareceu um dragão!

O método iniciar é igual para todas as fases; só a criação do inimigo muda.

Abstract Factory: famílias que combinam

Problema: você precisa criar vários objetos que têm de combinar entre si. Num jogo com tema claro e escuro, o botão, o fundo e o texto precisam ser todos do mesmo tema. Misturar um botão escuro com um fundo claro seria um defeito.

A fábrica abstrata é um objeto que sabe criar a família inteira:

class TemaClaro:
    def fundo(self):
        return "branco"

    def texto(self):
        return "preto"

    def botao(self, rotulo):
        return f"[ {rotulo} ] (cinza-claro)"


class TemaEscuro:
    def fundo(self):
        return "preto"

    def texto(self):
        return "branco"

    def botao(self, rotulo):
        return f"[ {rotulo} ] (azul-escuro)"


def desenhar_menu(fabrica):
    print(f"Fundo {fabrica.fundo()}, letras {fabrica.texto()}")
    print(fabrica.botao("Jogar"), fabrica.botao("Sair"))


desenhar_menu(TemaClaro())
desenhar_menu(TemaEscuro())

Fundo branco, letras preto
[ Jogar ] (cinza-claro) [ Sair ] (cinza-claro)
Fundo preto, letras branco
[ Jogar ] (azul-escuro) [ Sair ] (azul-escuro)

desenhar_menu nunca cita um tema. Para criar um tema "alto contraste", basta uma classe nova com os mesmos três métodos.

Builder: montar passo a passo

Problema: alguns objetos têm muitas partes opcionais. Um __init__ com dez parâmetros fica difícil de ler: Pizza("grande", True, False, True, ...) — o que é cada True?

O Builder monta o objeto em passos com nome. Cada método devolve o próprio construtor (return self), o que permite encadear as chamadas:

class Pizza:
    def __init__(self, tamanho, sabores, borda):
        self.tamanho = tamanho
        self.sabores = sabores
        self.borda = borda

    def __str__(self):
        return f"Pizza {self.tamanho} de {' e '.join(self.sabores)}, borda {self.borda}"


class MontadorDePizza:
    def __init__(self):
        self._tamanho = "média"
        self._sabores = []
        self._borda = "simples"

    def tamanho(self, valor):
        self._tamanho = valor
        return self

    def sabor(self, valor):
        self._sabores.append(valor)
        return self

    def borda(self, valor):
        self._borda = valor
        return self

    def pronta(self):
        if not self._sabores:
            raise ValueError("escolha pelo menos um sabor")
        return Pizza(self._tamanho, self._sabores, self._borda)


pedido = MontadorDePizza().tamanho("grande").sabor("calabresa").sabor("queijo").borda("catupiry").pronta()
print(pedido)
print(MontadorDePizza().sabor("frango").pronta())

Pizza grande de calabresa e queijo, borda catupiry
Pizza média de frango, borda simples

O Builder também pode validar antes de entregar: sem sabor, pronta() recusa.

Dica: Em Python, argumentos nomeados com valor padrão (aula 41) resolvem a maioria dos casos que pedem Builder: Pizza(tamanho="grande", borda="catupiry") já é legível. Use Builder quando a montagem tem muitos passos, regras ou repetições (como vários sabor(...)).

Singleton: um objeto só

Problema: alguns objetos devem existir uma única vez no programa inteiro, como as configurações do jogo ou o placar global. Se cada parte criar o seu, elas discordam entre si.

A forma clássica controla a criação com __new__ (aula 82):

class Configuracoes:
    _instancia = None

    def __new__(cls):
        if cls._instancia is None:
            cls._instancia = super().__new__(cls)
            cls._instancia.volume = 50
        return cls._instancia


a = Configuracoes()
b = Configuracoes()
a.volume = 80
print("b.volume =", b.volume)
print("a é b?", a is b)

b.volume = 80
a é b? True

Em Python há um jeito mais simples: um módulo já é um singleton. Quando você faz import config em vários arquivos, todos recebem o mesmo objeto módulo, carregado uma vez só. Basta colocar as variáveis em config.py:

import sys
import types

# simulando um arquivo config.py (no computador, seria um arquivo de verdade)
config = types.ModuleType("config")
config.volume = 50
sys.modules["config"] = config

import config as em_um_arquivo
import config as em_outro_arquivo

em_um_arquivo.volume = 80
print("Outro arquivo vê:", em_outro_arquivo.volume)
print("Mesmo módulo?", em_um_arquivo is em_outro_arquivo)

Outro arquivo vê: 80
Mesmo módulo? True

Atenção: Singleton é o padrão mais mal usado. Ele vira uma "variável global disfarçada": qualquer parte do programa muda o objeto e fica difícil descobrir quem mudou. Também atrapalha os testes, que não conseguem começar do zero. Prefira criar o objeto uma vez e passá-lo para quem precisa (inversão de dependência, aula 150).

Prototype: copiar um modelo

Problema: criar um objeto do zero dá trabalho (muitos campos, cálculos), mas você precisa de vários quase iguais. Em vez de montar cada um, você copia um protótipo pronto e muda só o que difere.

Em Python, o módulo copy (aula 47) faz o serviço. Use deepcopy quando o objeto tem listas ou dicionários dentro:

import copy


class Personagem:
    def __init__(self, nome, vida, itens):
        self.nome = nome
        self.vida = vida
        self.itens = itens

    def __repr__(self):
        return f"{self.nome}(vida={self.vida}, itens={self.itens})"


modelo = Personagem("Soldado", 100, ["espada", "escudo"])

soldado1 = copy.deepcopy(modelo)
soldado1.nome = "Soldado 1"
soldado2 = copy.deepcopy(modelo)
soldado2.nome = "Soldado 2"
soldado2.itens.append("arco")

print(modelo)
print(soldado1)
print(soldado2)

Soldado(vida=100, itens=['espada', 'escudo'])
Soldado 1(vida=100, itens=['espada', 'escudo'])
Soldado 2(vida=100, itens=['espada', 'escudo', 'arco'])

Com copy.copy (cópia rasa), a lista itens seria compartilhada: o arco do soldado 2 apareceria no modelo e no soldado 1 também.

Com dataclasses, a função replace cria uma cópia mudando alguns campos — um protótipo de uma linha:

from dataclasses import dataclass, replace


@dataclass(frozen=True)
class Ingresso:
    show: str
    setor: str
    preco: float


base = Ingresso("Festival de Música", "pista", 120.0)
vip = replace(base, setor="camarote", preco=350.0)
print(base)
print(vip)

Ingresso(show='Festival de Música', setor='pista', preco=120.0)
Ingresso(show='Festival de Música', setor='camarote', preco=350.0)

Quando usar cada um

  • Factory Method: a classe a criar depende de um dado (texto, opção) ou cada filha cria a sua versão.
  • Abstract Factory: vários objetos precisam combinar entre si (temas, plataformas).
  • Builder: objeto com muitas partes opcionais, passos ou validação.
  • Singleton: um recurso único de verdade; em Python, prefira um módulo ou passar o objeto adiante.
  • Prototype: criar do zero é caro e os objetos são parecidos; use copy.deepcopy ou dataclasses.replace.

Se nenhum desses problemas aparece, um simples Classe(...) é a melhor escolha.

2. Faça um MontadorDeSanduiche com os métodos pao(nome), recheio(nome) (pode ser chamado várias vezes) e pronto(), que devolve um texto como "Sanduíche no pão francês com queijo, presunto". Encadeie as chamadas.

5. Por que, em Python, muitas vezes não é preciso escrever uma classe Singleton?

Ver resposta

Porque um módulo já é carregado uma vez só: todo import do mesmo módulo
devolve o mesmo objeto. Basta guardar as configurações num arquivo como
